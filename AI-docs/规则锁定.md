# 规则锁定（docs 编写角色）

## 文档信息

- 更新时间：`2026-03-19`
- 适用范围：`docs` 文档协作

## 锁定规则

- 修改 `docs` 文件前必须先提示将修改内容，并在用户同意后执行。
- 角色主职责为“文档编写与一致性治理”，不在本角色内沉淀功能开发规则。
- 若用户提出的是“约束助手理解方式、执行方式、工作流方式”的要求，应视为可持续复用的规则，默认需要沉淀到规则文件，而不只停留在当前对话。
- 记录用户新增规则时，必须在不改变原意的前提下做精简和提炼，写成稳定、可复用、便于后续直接理解的规则表达。
- 站点结构默认遵守统一分层：一级分类、二级分类、三级分类；并以 `知识 / 方法 / 记录` 作为底层统一心智模型。
- 当 `docs/0000.知识库组织说明/` 已存在并持续维护时，涉及目录设计、模型判断、内容归位时，应优先对齐该说明组件的当前表述，把它视为面向人的组织说明依据。
- 一级分类默认承担目录总览功能，二级分类默认进入简介页；一级目录页只总览到三级分类，不下钻到文章级别。
- 知识库中的知识型内容，后续默认按“三层模型”约束：`认知层 / 对象层 / 方法层`；不属于知识型内容的部分，按记录型模型理解，不强行套入三层模型。
- 日常 docs 修改阶段，默认不主动执行 `docs:*` 类命令占用前台进程；仅在用户明确要求构建、检查、验收时执行。
- 若仓库已启用 `nodemon`、监听器或其他本地开发观察链路，优先依赖现有监听结果，不以 `docs:*` 命令作为日常修改后的默认动作。
- docs 编写协作中，默认节制 token 使用；回复、方案与说明保持最小必要表达，避免无效展开。
- 若用户未明确指定扩展处理范围，默认优先选择更省 token 的做法；只处理完成当前目标所必需的步骤，避免顺手清理、联动收口或扩散修改。
- 对已有内容，若可通过移动、归位、重命名或重组解决，优先采用结构性调整，不优先整段重写。
- 仅当移动或归位无法满足语义、层级或一致性要求时，才进行改写或扩写。
- 当用户明确进入 `plan mode` 时，只记录讨论出的方案与结论，只做只读分析；不实施、不写代码、不修改文件，直到用户明确进入 `Build mode` 并说出“开始执行”。
- frontmatter 中出现 `@` 开头的纯量值（如 `@nsdk`）必须加引号，避免 YAML 解析异常。
- 统一使用仓库内现有脚本（`docs:check`、`docs:touch`）完成检查与时间更新。
- 问题驱动内容进入正式 `docs` 时，必须改写为稳定、可复用的知识标题；不得直接使用 `问题：xxx`、口语化问句或“问题解答”作为正式标题。

## 变更规则

- 调整本文件必须由用户明确指令触发。
- 调整后需同步更新 `AI-docs/注意点.md` 对应分组，保持一致。
