# 注意点（docs 编写角色）

## 文档信息

- 更新时间：`2026-03-19`
- 适用范围：`docs` 目录文档编写与治理

## 使用规则

- 本文件用于沉淀可长期复用的文档协作规则。
- 新增规则按分组追加，不覆盖既有语义。
- 与 `AI-docs/规则锁定.md` 冲突时，以锁定规则为准。

## 分组规则

### A. frontmatter 规则

- `00.目录.md` 保持目录页字段完整：`title/date/catalogue/layout/permalink/path/desc/sidebar/article`。
- `00.简介.md` 保持基础字段完整：`title/date/permalink/categories/tags`。
- `tags` 或 `categories` 中若值以 `@` 开头，必须写为带引号字符串（如 `'@nsdk'`）。
- 新增文档默认写 `date`，并通过 `pnpm docs:touch` 更新。

### B. permalink 与链接规则

- 新增文档先确认 permalink 不冲突。
- 默认不使用尾斜杠风格（与仓库现有主风格保持一致）。
- 文档内链接优先指向 permalink，而非物理路径。

### C. 命名与目录规则

- 目录和文件优先沿用数字前缀排序习惯（如 `10.xxx`、`20.xxx`）。
- `00.目录.md` 的 `title` 与所在目录语义保持一致。
- `00.简介.md` 标题建议为“XX简介”风格，减少入口页命名歧义。
- 一级、二级、三级分类不通过物理父子文件夹嵌套表达层级，统一平铺在 `docs/` 根目录，通过编号表达归属关系。
- 四级及以后，才允许在某个三级分类目录内部继续使用子文件夹细分内容。
- 一级、二级分类只保留 `00.目录.md`；三级分类保留 `00.目录.md + 00.简介.md + 正文页`。

### D. 内容编写规则

- 优先写“可持续补充”的结构化内容（表格、清单、模板）。
- 当用户强调“汇总 + 分类拆分”时，入口页只做总览，分类内容放独立文件。
- 写法以可复用、可检索为目标，避免一次性口语化说明。
- 当 `docs/0000.知识库组织说明/` 已明确组织方式时，后续内容编写优先与其术语、层级、模型判断保持一致。
- `docs` 下文档默认采用“精炼要点 + 延伸阅读”的写法，保证内容具备延展性。
- `延伸阅读` 默认包含三类链接：官方文档、标准/规范、仓库内相关文档。
- 当正文中已有明确的延伸方向时，可直接在对应文字处添加内链或外链，减少读者来回查找成本。
- 知识说明类文档除要点外，尽量补充“最小可执行示例”，让读者知道如何实际使用。
- 枚举型内容（如表单类型、API 分类、策略对比）优先使用表格梳理；表格无法完整承载时，再通过链接延伸。
- 专业术语若存在高质量外部资料，优先直接加链接，降低二次检索成本。

### E. 模型约束规则

- 知识型内容默认优先按“三层模型”判断主归属：`认知层 / 对象层 / 方法层`。
- `认知层` 主要承接“怎么理解”的内容；`对象层` 主要承接“在处理什么”的内容；`方法层` 主要承接“怎么做、怎么推进”的内容。
- 一篇内容默认只设一个主模型，其他模型相关时优先通过一句话提示或内链处理，不重复展开整篇正文。
- 知识库中的知识型内容页默认按三层模型约束编写；主题页的 `00.简介.md` 可通过简短说明或标签体现主模型，帮助读者快速理解页面职责。
- `经历与感悟`、`人生记录` 等记录型内容不强行套入三层模型，应按“记录型模型”理解：经历、感受、提炼。

### F. 检查与验证规则

- 每次文档修改后默认执行：`pnpm docs:check`。
- 影响站点渲染或目录结构时，补充执行：`pnpm docs:build`。
- 若发现可自动拦截的问题，应优先固化到脚本检查中。

### G. 协作流程规则

- 默认先给方案，再修改。
- 默认最小改动，不做无关重写。
- 默认节制 token 使用，回复、方案与结果反馈尽量短而完整，不做无效展开。
- 若用户没有明确要求一并清理、校正或联动调整，默认只做完成当前目标所需的最小修改，避免产生额外 token 消耗。
- 对已有内容，能通过移动、归位、重命名或重组解决时，优先结构调整，不优先重写正文。
- 只有当结构性移动无法满足语义、层级或一致性要求时，才进行改写或扩写。
- 当用户明确进入 `plan mode` 时，默认只输出方案、结论与分析结果，不落盘、不实施、不写代码；只有在用户明确进入 `Build mode` 且说出“开始执行”后，才切换为执行态。
- 结果反馈包含：改了什么、在哪个文件、是否通过检查。
- 用户后续若以 `问题：xxx` 的格式提问，默认按“先回答问题，再将结论按现有文档规范补入最合适的 docs 文件”处理。
- 当问题内容进入正式 `docs` 时，必须改写为稳定知识标题，不直接使用 `问题：xxx`、口语化问句或“问题解答”作为标题。
- 如果需要保留提问语境，应放在正文引导语中表达，而不是放到文档标题或章节标题里。

### H. 前端模块规范

- `docs/01.前端` 下各子模块优先保持统一结构：`00.目录.md`、`00.简介.md`、速查 / 原理 / 方案 / 排查 / 面试。
- 文件命名应尽量让人一眼看出用途，优先使用：`一览`、`速查要点`、`原理与机制`、`方案`、`问题`、`优化`、`面试高频问题`。
- 目录结构优先规范化，再补知识点内容。
- 当前协作重点优先放在前端相关内容，尤其是 `CSS`、`JavaScript`、`Web`、`V8`。
