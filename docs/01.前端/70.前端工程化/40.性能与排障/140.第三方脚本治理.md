# 第三方脚本治理

## 阅读建议

- 这页重点不是简单区分 SDK 类型，而是理解第三方脚本为什么经常成为性能、稳定性和安全边界的薄弱点。

## 核心目标

- 理解第三方脚本治理要同时关注接入必要性、加载时机、失败降级、版本变更和观测能力。

## 常见第三方脚本类型

| 类型           | 常见例子                   | 主要风险                 |
| -------------- | -------------------------- | ------------------------ |
| 统计埋点脚本   | Analytics、埋点 SDK        | 阻塞、重复上报、口径漂移 |
| 登录支付脚本   | OAuth、支付、风控 SDK      | 主链路依赖、失败不可控   |
| 地图富媒体脚本 | 地图、视频、客服、可视化库 | 体积大、初始化慢         |
| A/B 实验脚本   | 实验平台、个性化推荐       | 首屏抖动、结果不可复现   |

## 治理主线

1. 先问这段脚本是不是必须接入。
2. 明确它是否在首屏关键链路上。
3. 设计异步加载、失败降级和超时兜底。
4. 记录版本、责任人、影响页面和回滚方式。

## 接入时重点关注什么

- 尽量避免把第三方脚本直接塞进首屏同步执行链路。
- 脚本加载失败时，要保证页面主体功能还能继续运行。
- 对高风险脚本建立超时、重试和兜底提示。
- 对脚本体积、错误率和调用耗时建立监控。

## 最小示例

```text
主业务先可用 -> 第三方脚本异步加载 -> 失败可降级 -> 指标持续观测
```

## 常见治理维度

| 维度     | 重点问题                             |
| -------- | ------------------------------------ |
| 必要性   | 是否真的需要在当前页面接入           |
| 时机     | 首屏加载、交互触发、空闲加载谁更合适 |
| 稳定性   | 失败、超时、接口变更如何处理         |
| 版本管理 | 谁升级、谁验收、谁负责回滚           |
| 可观测性 | 是否能看到错误率、耗时和业务影响     |

## 常见误区

- 看到官方接入示例就直接同步插入页面头部。
- 第三方脚本挂了，主页面也跟着白屏或核心按钮不可用。
- 脚本越来越多，却没有统一清单和责任归属。
