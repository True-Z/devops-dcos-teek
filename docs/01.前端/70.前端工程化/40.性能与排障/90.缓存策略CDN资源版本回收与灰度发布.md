# 缓存策略 CDN 资源版本回收 与灰度发布

## 阅读建议

- 这页重点不是单独讲缓存或发布，而是把“资源怎么缓存、怎么回收、怎么安全放量”放到一条上线链路里理解。

## 核心目标

- 理解为什么静态资源发布如果只考虑构建，不考虑缓存和回收，线上很容易出错。

## 缓存策略怎么分

| 类型           | 更适合什么                    |
| -------------- | ----------------------------- |
| 强缓存         | 带 hash 的静态资源            |
| 协商缓存       | 可复用但可能变动的资源        |
| 不缓存或短缓存 | HTML 入口、需要快速切换的配置 |

## 为什么 HTML 和静态资源通常策略不同

- HTML 入口决定资源引用关系，通常要更容易更新。
- 带内容 hash 的 JS/CSS 资源更适合长缓存。

## CDN 在解决什么问题

- 提升静态资源分发速度
- 降低源站压力
- 让不同区域用户更快拿到资源

## 资源版本回收为什么常被忽略

- 因为资源一旦带版本不断累积，如果没有回收策略，存储、回滚和兼容窗口都会越来越复杂。
- 但也不能回收过快，否则旧 HTML 还引用旧资源时就会直接 404。

## 推荐主线

1. HTML 入口保持相对短缓存。
2. 带 hash 的静态资源走长缓存。
3. 保留最近若干稳定版本，支持回滚。
4. 资源回收时考虑旧页面和 CDN 缓存窗口。

## 灰度发布怎么理解

- 灰度发布不是“偷偷上线”，而是控制新版本只让部分用户或部分流量先命中。
- 它的价值是降低全量发布带来的风险半径。

## 最小示例

```text
新版本先放少量流量 -> 观察错误率与关键指标 -> 再逐步全量
```

## 常见误区

- HTML 也走超长缓存，导致入口长期不刷新。
- 资源刚发布就立刻回收旧版本，回滚失败。
- 灰度只做流量切分，不看监控与回滚条件。
