# 脚本错误上报与 sourcemap 发布策略

## 阅读建议

- 这页重点不是只讲采集或只讲 sourcemap，而是把“错误怎么报、怎么还原、怎么跟版本对应”放在同一条链路里理解。

## 核心目标

- 理解线上脚本错误如果没有版本映射和 sourcemap 配合，很多告警最终都只能停留在压缩代码层面。

## 一条最小链路

```text
采集错误 -> 带上版本与环境 -> 上传 sourcemap -> 平台反解 -> 定位源码与发布版本
```

## 设计时重点关注什么

| 方向      | 重点问题                               |
| --------- | -------------------------------------- |
| 采集内容  | 错误堆栈、页面、版本、环境、用户上下文 |
| 版本绑定  | 错误必须和构建产物版本一一对应         |
| sourcemap | 如何上传、保存、访问权限如何控制       |
| 回滚协作  | 版本回滚后是否还能还原历史错误         |

## 推荐治理主线

1. 上报错误时必须带版本号和环境信息。
2. 构建产物和 sourcemap 保持同版本关联。
3. sourcemap 上传要自动化，不依赖人工补传。
4. 平台反解失败要能快速发现和补救。

## 最小示例

```json
{
  "release": "web-1.4.2",
  "env": "prod",
  "page": "/order/checkout"
}
```

- 没有稳定的 `release` 字段，后续错误还原和回滚分析都会很吃力。

## 常见误区

- 只上报 message，不带版本和堆栈上下文。
- sourcemap 生成了，但没人上传或版本对不上。
- 为了方便直接对外暴露 sourcemap，忽略安全和访问控制。
