# 性能预算 产物阈值 与 CI 质量门禁

## 阅读建议

- 这页重点不是“限制越多越好”，而是建立能持续执行的质量门禁。

## 核心目标

- 理解为什么性能治理如果没有阈值和自动化门禁，最终很容易失效。

## 什么是性能预算

- 性能预算可以理解成团队提前约定的性能上限，比如首屏资源大小、关键指标目标、主包体积阈值。
- 它的意义在于：把“感觉变慢了”变成“可以被验证的约束”。

## 常见预算维度

| 维度     | 常见限制                   |
| -------- | -------------------------- |
| 主包体积 | 初始 JS/CSS 不超过某个阈值 |
| 页面指标 | LCP、CLS、TTFB 有目标值    |
| 资源数量 | 首屏关键请求数受控         |
| 执行成本 | 长任务数量、初始化脚本时长 |

## 产物阈值为什么重要

- 因为很多性能问题在业务上线前就已经体现在打包结果里。
- 如果 bundle 体积、chunk 数量、公共依赖膨胀没人拦，线上一定会慢慢失控。

## CI 质量门禁怎么理解

- CI 不只是跑单测，还可以对包体积、lint、类型、构建结果做强制检查。
- 一旦超过阈值，就不允许合并或发版。

## 最小主线

```text
设定预算 -> 自动检测 -> 超阈值失败 -> 回到代码与依赖层优化
```

## 常见门禁项

1. Lint 和类型检查
2. 单测和关键 E2E
3. 构建是否通过
4. 主包/关键 chunk 体积阈值
5. 性能指标回归检查

## 常见误区

- 只有 warning，没有真正阻断。
- 阈值拍脑袋定，团队没人维护。
- 只看体积，不看运行时执行成本。
