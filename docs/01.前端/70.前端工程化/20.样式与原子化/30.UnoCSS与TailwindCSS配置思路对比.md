# UnoCSS 与 TailwindCSS 配置思路对比

## 阅读建议

- 这页重点不是比较谁更好，而是帮助你理解：为什么 UnoCSS 让人感觉直观，TailwindCSS 却更像一套设计系统配置。

## 核心目标

- 看完后能知道两者在 spacing、响应式、预设和扩展思路上的本质区别。

## 一句话区分

- UnoCSS 更像“规则驱动，写法直觉更强”。
- TailwindCSS 更像“设计 token 驱动，体系感更强”。

## 配置思路对比

| 维度         | UnoCSS                     | TailwindCSS                 |
| ------------ | -------------------------- | --------------------------- |
| 心智模型     | 规则更直接                 | token 体系更明显            |
| spacing 理解 | 更容易让人觉得接近直觉映射 | 明显依赖预设 scale          |
| 扩展方式     | 规则、预设、快捷方式       | `theme`、`extend`、`plugin` |
| 响应式       | 规则直接叠前缀             | 断点体系固定感更强          |
| 团队统一性   | 灵活，但需要自控           | 更适合设计系统统一          |

## 为什么 UnoCSS 让人觉得直观

- 很多时候写法更像“看到什么写什么”。
- 规则驱动下，开发者更容易把类名直接联想到结果。

## 为什么 TailwindCSS 容易显得难懂

- 因为它不是只在解决“我要一个样式”。
- 它同时还在解决：
  - 设计 token
  - 团队统一
  - 组件库可维护性
  - 构建期类名提取

## spacing 这一点怎么理解

| 问题   | UnoCSS 常见感受 | TailwindCSS 常见感受 |
| ------ | --------------- | -------------------- |
| `p-10` | 更像“直觉数字”  | 更像“第 10 档 token” |

- 所以你会觉得 Uno 更顺手，而 Tailwind 更绕。
- 但 Tailwind 的优势就是“整个系统更统一”。

## 项目里怎么选更稳

| 场景                     | 更推荐                     |
| ------------------------ | -------------------------- |
| 个人快速开发             | UnoCSS 更轻快              |
| 组件库 / 团队协作        | TailwindCSS 更稳           |
| 已经在用 Tailwind 的项目 | 先顺着它，不急着改底层语义 |

## 对 `@nsdk/web-ele` 这类项目的建议

- 如果已经在用 TailwindCSS
- 更推荐：
  - 接受它的 spacing token 体系
  - 需要补值时只做 `extend`
  - 不强改成 Uno 的数字直觉模型

## 最小判断

```text
想要更直觉 -> UnoCSS
想要更体系化 -> TailwindCSS
项目已用 Tailwind -> 优先顺着系统走
```

## 常见误区

- 以为 Uno 直观，就一定更适合团队项目。
- 以为 Tailwind 难懂，就说明配置一定有问题。
- 不区分“个人体验”和“团队长期维护成本”。

## 从 UnoCSS 切到 Tailwind 最容易踩的坑

| 坑点                   | 为什么会踩                                     |
| ---------------------- | ---------------------------------------------- |
| 把数字当像素           | Tailwind 的数字更多是 token 编号，不是直接像素 |
| 动态拼类名             | Tailwind 依赖静态扫描，运行时拼接容易失效      |
| 一开始就大改 spacing   | 会破坏默认体系，团队认知容易错位               |
| 忽略 `extend` 只想重写 | 很多需求其实增量扩展就够了                     |
| 不看预设直接改         | 容易和已有组件库 / 设计系统冲突                |

## 迁移时更稳的做法

1. 先接受 Tailwind 的默认 spacing 语义。
2. 缺什么值，再通过 `extend` 补什么值。
3. 先把动态类名改成枚举映射。
4. 最后再考虑是否真的要改底层 token 体系。
