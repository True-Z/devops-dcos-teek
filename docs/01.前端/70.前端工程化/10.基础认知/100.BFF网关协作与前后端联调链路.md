# BFF 网关协作与前后端联调链路

## 阅读建议

- 这页重点不是只分概念，而是理解请求链路里每一层的职责边界。

## 核心目标

- 理解前端、BFF、网关、后端服务之间怎么协作，为什么很多团队需要中间层。

## BFF 是什么

- BFF 可以理解成为前端场景定制的后端聚合层。
- 它的重点不是替代后端服务，而是把前端页面真正需要的数据形态整理好。

## 网关更像做什么

- 网关更偏入口治理：鉴权、路由转发、限流、灰度、统一策略。
- 它通常不适合承接太多页面级拼装逻辑。

## 一张表看边界

| 角色     | 更适合负责什么             |
| -------- | -------------------------- |
| 前端     | 展示、交互、页面状态       |
| BFF      | 页面级数据聚合、裁剪、适配 |
| 网关     | 统一接入、鉴权、转发、治理 |
| 后端服务 | 领域能力、核心业务逻辑     |

## 前后端联调链路怎么理解

```text
前端页面 -> BFF / 网关 -> 后端服务 -> 返回聚合结果 -> 页面渲染
```

- 实际联调时更重要的是：接口契约清不清晰、Mock 是否可用、错误路径能不能提前演练。

## 为什么会需要 BFF

- 一个页面要拼多个后端接口
- 后端接口字段过重，不适合直接给前端
- 不同终端需要不同数据结构

## 联调的关键点

1. 先定接口契约
2. 再准备 Mock 或联调环境
3. 明确错误码、空态、超时策略
4. 联调时不仅测成功路径，也测失败路径

## 常见误区

- 把所有逻辑都堆进 BFF，最后变成新的大单体。
- 前端只验证 happy path，错误链路全靠线上暴露。
- 网关、BFF、后端职责不清，出了问题互相甩锅。
