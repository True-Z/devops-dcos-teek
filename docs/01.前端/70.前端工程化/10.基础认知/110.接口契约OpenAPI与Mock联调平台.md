# 接口契约 OpenAPI 与 Mock 联调平台

## 阅读建议

- 这页重点不是工具名罗列，而是理解“接口契约为什么要前置，以及怎样减少联调摩擦”。

## 核心目标

- 理解接口契约、OpenAPI、Mock、联调平台在协作链路中的职责边界。

## 什么是接口契约

- 接口契约可以理解为前后端对请求结构、响应结构、错误码语义的共同约定。
- 它不是“文档可有可无”，而是联调和自动化生成的基础。

## OpenAPI 在解决什么问题

- OpenAPI 让接口定义更标准化、机器可读。
- 一旦定义标准化，就更容易做：
  - 文档生成
  - SDK 生成
  - Mock 生成
  - 契约校验

## Mock 平台更适合做什么

- 当真实后端未完成或环境不稳定时，Mock 平台可以让前端先跑页面和交互。
- 它解决的是“协作节奏错位”问题，不是长期替代真实后端。

## 联调平台更像做什么

- 联调平台更偏协作中台：
  - 管接口文档
  - 管环境地址
  - 管 Mock 与真实服务切换
  - 管调试与测试链路

## 一张表看边界

| 能力     | 更适合负责什么           |
| -------- | ------------------------ |
| 接口契约 | 定义字段与语义边界       |
| OpenAPI  | 标准化描述与自动化生成   |
| Mock     | 提前联动前端页面开发     |
| 联调平台 | 管理调试、环境和协作流程 |

## 最小主线

```text
定义契约 -> 生成文档/Mock -> 前端开发联调 -> 接真实服务 -> 回归验证
```

## 为什么这块重要

- 很多所谓“联调慢”本质不是技术问题，而是契约不清晰、错误码不统一、环境不可控。
- 契约越前置，前端和后端越容易并行推进。

## 常见误区

- 契约只写成功返回，不定义错误结构。
- Mock 数据长期不维护，最后和真实接口完全脱节。
- 联调时只测 happy path，不测空态、错误码、超时和权限失败。
