# 版本管理与 Changesets 发布协作

## 阅读建议

- 这页重点不是某个工具命令，而是团队怎样把“变更 -> 版本 -> 发布说明 -> 发布动作”串起来。

## 核心目标

- 理解为什么多包项目里版本管理不能靠人工口头约定。

## 为什么需要版本管理协作

- 当仓库里有多个包、多个应用、多个发布目标时，最大问题不是“怎么发”，而是“这次改动应该涨哪个版本、影响谁、怎么记录”。

## Changesets 解决什么问题

| 问题               | Changesets 的价值         |
| ------------------ | ------------------------- |
| 版本提升靠人工判断 | 用变更记录驱动版本变更    |
| 发布说明没人写     | 变更说明跟随代码进入仓库  |
| 多包联动难追踪     | 能明确哪些包被影响        |
| 发版流程不稳定     | 能配合 CI/CD 形成标准链路 |

## 最小流程

```text
提交功能 -> 记录 changeset -> 合并代码 -> 生成版本变更 -> 发布产物
```

## 协作主线

1. 开发提交功能时补 changeset
2. 合并前确认影响包与版本级别
3. 发版时统一生成 changelog 和版本号
4. 配合流水线执行构建、测试、发布

## 常见误区

- 把版本管理只当成“改 package.json 里的数字”。
- 发版前才临时补记录，最后说明失真。
- 多包一起改，却没有明确哪个包该升级什么级别。

## 面试回答建议

- 先讲多包协作为什么需要标准化版本管理。
- 再讲 Changesets 如何让版本、变更说明、发布动作串起来。
- 最后补它如何和 CI/CD、monorepo 一起工作。
