# 大文件下载的断点续传与分片方案

## 阅读建议

- 如果你只是在做普通文件下载，优先先看 [前端下载方案与流式传输](/fe/web-download-streaming)，这页更偏大文件增强方案。
- 如果你现在要解决弱网中断、失败重试、暂停恢复、下载进度不准这些问题，重点看“常见方案对比”“服务端必须配合什么”“前端实现思路”。

## 核心目标

- 在大文件下载场景下，同时兼顾可恢复性、稳定性、内存占用和用户体验。

## 模块定位

- 这页重点是“大文件下载为什么不能只靠普通 `blob` 下载，以及断点续传和分片下载该怎么设计”，适合和浏览器流式能力、HTTP 范围请求一起理解。

## 先区分两个概念

| 概念     | 核心含义                                 | 典型用途                             | 关键前提                 |
| -------- | ---------------------------------------- | ------------------------------------ | ------------------------ |
| 分片下载 | 把一个文件拆成多个区间分别请求           | 提升大文件拉取灵活性，支持并发与重试 | 服务端支持范围请求       |
| 断点续传 | 下载中断后，从已完成位置继续拉取剩余部分 | 弱网恢复、失败重试、暂停继续         | 前后端都能识别已完成区间 |

- 分片下载不一定等于断点续传，但断点续传通常会利用分片或区间记录能力。
- 如果服务端不支持 `Range`，前端很难做真正可靠的断点续传。

## 常见方案对比

| 方案             | 适合场景                                 | 优点                                 | 局限                                     |
| ---------------- | ---------------------------------------- | ------------------------------------ | ---------------------------------------- |
| 浏览器原生下载   | 公开资源、简单附件、大文件但无需前端控制 | 最稳定，浏览器接管，前端实现成本最低 | 很难控制进度、错误处理、暂停与恢复       |
| 单连接流式下载   | 大文件、需要展示实时进度                 | 可逐块读取，体验优于一次性 `blob`    | 中断后一般需要重新开始，续传能力弱       |
| `Range` 断点续传 | 下载易中断、需要失败后继续               | 可从指定字节继续下载，恢复成本低     | 依赖服务端支持范围请求与文件一致性校验   |
| 并发分片下载     | 超大文件、弱网、多次重试需求明显         | 可按片重试、控制并发、提升整体稳定性 | 实现复杂，最终合并策略不当仍会有内存压力 |

## 服务端必须配合什么

| 响应头 / 能力          | 作用                         | 说明                                  |
| ---------------------- | ---------------------------- | ------------------------------------- |
| `Accept-Ranges: bytes` | 声明支持范围请求             | 没有它，前端通常只能整文件重下        |
| `Content-Length`       | 提供资源总大小               | 用于计算下载百分比和区间边界          |
| `Content-Range`        | 返回当前片段覆盖的字节范围   | 范围响应常见于 `206 Partial Content`  |
| `ETag` / 文件版本标识  | 保证续传时资源还是同一个版本 | 防止文件内容变化后继续拼接旧分片      |
| 稳定鉴权方式           | 保证多次分片请求都能访问     | 可使用 Cookie、签名 URL、Bearer Token |

- 如果服务端动态生成文件但没有稳定版本标识，续传后可能出现文件拼接错乱。
- 如果服务端对范围请求支持不完整，前端即使发了 `Range` 也可能拿到整文件响应。
- 生产实践里，前端通常还需要和服务端约定分片大小上限、过期时间、失败码语义。

## 前端实现思路

### 1. 先拿到文件元信息

- 先确认文件总大小、文件名、是否支持 `Range`。
- 如果服务端没有返回 `Content-Length`，前端可以显示“已下载字节数”，但很难给出准确百分比。

### 2. 维护已下载区间

- 最简单的方式是只记录“已完成到哪个字节”，适合单连接断点续传。
- 更完整的方式是记录多个已完成分片区间，适合并发分片下载。
- 区间状态可放在内存、`IndexedDB` 或业务侧任务状态表中。

### 3. 失败时只重试未完成部分

- 网络中断、鉴权刷新、页面短暂抖动，不应该让整个文件重新下载。
- 重试时带上新的 `Range` 区间，只请求缺失片段。

### 4. 汇总进度

- 单连接续传时，进度通常是“已完成字节 / 总字节”。
- 并发分片时，进度要汇总所有已完成片段，而不是只看当前请求。

### 5. 处理暂停与恢复

- 暂停本质上是中止当前请求并保留已完成区间。
- 恢复本质上是基于已完成区间重新发起剩余请求。

### 6. 关注最终落盘方式

- 如果最后仍把所有分片拼成一个 `Blob` 再下载，超大文件依然会占用大量内存。
- 更稳的方案是边下边写磁盘，或让浏览器 / 原生容器接管最终保存。

## 最小示例

### 单段断点续传

```js
async function resumeDownload(url, start = 0) {
  const res = await fetch(url, {
    headers: {
      Range: `bytes=${start}-`,
    },
  })

  if (![200, 206].includes(res.status) || !res.body) {
    throw new Error('下载失败')
  }

  const reader = res.body.getReader()
  const chunks = []
  let loaded = start

  while (true) {
    const { done, value } = await reader.read()
    if (done) break

    chunks.push(value)
    loaded += value.length
    console.log('已下载字节数:', loaded)
  }

  return {
    loaded,
    blob: new Blob(chunks),
  }
}
```

- 这个示例只演示“从某个字节继续下载”的基本思路。
- 生产环境还需要处理文件名、进度持久化、失败重试、版本一致性校验。

### 并发分片下载

```js
async function downloadChunk(url, start, end) {
  const res = await fetch(url, {
    headers: {
      Range: `bytes=${start}-${end}`,
    },
  })

  if (res.status !== 206) {
    throw new Error('分片下载失败')
  }

  return new Uint8Array(await res.arrayBuffer())
}

async function downloadByChunks(url, fileSize, chunkSize = 1024 * 1024) {
  const tasks = []

  for (let start = 0; start < fileSize; start += chunkSize) {
    const end = Math.min(start + chunkSize - 1, fileSize - 1)
    tasks.push(downloadChunk(url, start, end))
  }

  const parts = await Promise.all(tasks)
  return new Blob(parts)
}
```

- 这个版本是教学版，只展示“按区间拉取”的核心思路。
- 真正落地时通常不会一次性把所有分片全并发出去，而是会限制并发数，例如 `3 ~ 6` 个。
- 如果最终仍返回 `Blob`，说明它更适合中等大文件，不适合无限放大到超大文件场景。

## 常见问题

### 为什么我发了 `Range` 还是整文件响应

- 常见原因是服务端没有正确支持范围请求，或者 CDN / 网关把响应处理成了普通 `200`。

### 为什么分片越多反而越慢

- 分片过小会放大请求开销、连接开销和服务端压力。
- 并发过高还可能触发浏览器连接限制、服务端限流或带宽竞争。

### 为什么进度条有时不准

- 如果缺少 `Content-Length`，或者服务端是动态流式生成内容，前端只能估算或展示已下载量。

### 为什么断点续传后文件损坏

- 常见原因是文件版本变了、区间拼接顺序错了，或者前后两次下载的资源并不是同一份内容。

## 实施建议

- 小文件或一次性导出，优先仍用普通下载方案，不要无意义上分片。
- 分片大小一般从 `1MB ~ 8MB` 起步评估，再根据带宽、服务端负载和失败率调整。
- 并发数建议保守起步，通常从 `3 ~ 6` 个任务开始，不要默认拉满。
- 如果目标是超大文件稳定下载，优先评估“前端记录区间 + 服务端 `Range` + 流式落盘”组合方案。
- 如果目标是广泛兼容，准备降级路径：支持增强下载时走断点续传，不支持时退回浏览器原生下载。
