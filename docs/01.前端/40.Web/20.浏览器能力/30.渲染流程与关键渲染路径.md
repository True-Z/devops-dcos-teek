# Web 渲染流程与关键渲染路径

## 阅读建议

- 这页适合按“解析 -> 布局 -> 绘制 -> 合成”主线阅读，不建议只记术语。
- 如果你当前主要在排查白屏、卡顿、掉帧，优先看“渲染阶段速览”和“合成层是什么”。

## 核心目标

- 理解浏览器把资源变成像素的完整链路。
- 理解为什么有的修改只触发合成，有的修改会触发布局和重绘。

## 渲染阶段速览

| 阶段           | 浏览器在做什么     | 常见卡点                 |
| -------------- | ------------------ | ------------------------ |
| HTML 解析      | 构建 DOM           | 主文档过大、同步脚本阻塞 |
| CSS 解析       | 构建 CSSOM         | 阻塞渲染的样式资源       |
| Render Tree    | 合并可见节点与样式 | 样式计算复杂             |
| Layout         | 计算几何信息       | 频繁读写布局属性         |
| Paint          | 生成绘制指令       | 大面积绘制、复杂阴影     |
| Layer / Raster | 图层切分与栅格化   | 图层过多、位图过大       |
| Composite      | 合成图层到屏幕     | 动画抖动、合成压力       |

## 从输入 URL 到页面可见

```text
请求 HTML -> 解析 HTML -> 遇到 CSS/JS 再请求 -> DOM + CSSOM -> Render Tree -> Layout -> Paint -> Composite -> 首屏可见
```

- JavaScript 会影响解析和渲染节奏，所以“请求完成”不等于“页面已经渲染完成”。

## 关键渲染路径是什么

- 关键渲染路径可以理解为：浏览器为了把首屏内容展示出来，必须走完的最短渲染链路。
- 这条路径越长、阻塞越多，首屏越慢。

### 关键点

- CSS 会阻塞渲染，因为浏览器需要先知道节点长什么样。
- 同步 JavaScript 可能阻塞 HTML 解析，也可能读写 DOM/CSSOM 影响渲染时机。
- 首屏真正重要的是“关键资源先到、关键内容先显示”，不是所有资源都同时到齐。

## DOM、CSSOM、Render Tree 是什么关系

| 结构        | 作用                    | 是否直接上屏           |
| ----------- | ----------------------- | ---------------------- |
| DOM         | 表示文档结构            | 否                     |
| CSSOM       | 表示样式规则            | 否                     |
| Render Tree | 合并可见 DOM 与样式结果 | 是后续布局和绘制的基础 |

- `display: none` 的节点通常不会进入 Render Tree。
- 所以“页面里有 DOM”不代表“它一定参与渲染”。

## Layout 在做什么

- Layout 负责计算元素的大小、位置、盒模型和相对关系。
- 只要几何信息变了，通常就要重新布局。

### 常见触发点

- 改宽高、边距、定位
- 改文字内容导致尺寸变化
- 读取 `offsetWidth`、`getBoundingClientRect()` 等布局信息后又立刻写样式

## Paint 在做什么

- Paint 负责把边框、背景、文字、阴影这些外观转成绘制指令。
- 它不一定重新算位置，但会重新把视觉结果画出来。

### 常见高开销场景

- 大面积背景变化
- 复杂阴影、滤镜、模糊
- 大图、多层半透明叠加

## 合成层是什么

- 合成层可以理解为浏览器为某些元素单独准备的一层“可独立合成的位图层”。
- 当元素变化只发生在合成阶段时，浏览器可以跳过布局和重绘，只更新图层合成结果。

### 为什么它重要

- 动画如果只改 `transform` 或 `opacity`，更容易停留在合成阶段。
- 这样主线程压力更小，掉帧概率通常更低。

### 但不是越多越好

- 图层也要占内存。
- 图层过多会带来管理和栅格化成本，反而可能更卡。

## 合成、重绘、重排怎么区分

| 类型             | 影响范围       | 常见触发               |
| ---------------- | -------------- | ---------------------- |
| 重排 / Layout    | 位置和尺寸     | 宽高、定位、文字流变化 |
| 重绘 / Paint     | 外观但不改布局 | 颜色、背景、阴影       |
| 合成 / Composite | 图层合成结果   | `transform`、`opacity` |

- 理想情况不是“完全没有渲染开销”，而是尽量把高频变化压到合成阶段。

## 最小示例

```js
const box = document.querySelector('.box')

box.style.transform = 'translateX(100px)'
box.style.opacity = '0.8'
```

- 这类修改通常比直接改 `left/top` 更容易走合成阶段。

## 渲染性能排查主线

1. 先看是不是资源阻塞了首屏。
2. 再看是不是 JavaScript 执行太重，卡住了解析和渲染。
3. 再区分是 Layout 问题、Paint 问题，还是图层合成问题。
4. 最后用 DevTools 的 Performance、Layers、Rendering 面板确认瓶颈。

## 常见误区

- 以为“加载完成”就等于“已经渲染完成”。
- 以为所有动画都天然高性能，不看是否触发布局和绘制。
- 以为合成层越多越好，忽略内存和图层管理成本。
