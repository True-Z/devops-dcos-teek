# 前端下载方案与流式传输

## 阅读建议

- 如果你现在只想解决业务下载，先看“常见下载方案对比”和“选型建议”。
- 如果你关注大文件、进度条、内存占用，再重点看“流式传输如何实现”和“服务端配合点”。

## 核心目标

- 在下载体验、内存占用、可控性、兼容性之间选到合适方案。

## 模块定位

- 这页重点是“前端如何发起下载、不同方案怎么取舍、流式传输怎么落地”，适合和浏览器能力、网络响应头一起理解。

## 常见下载方案对比

| 方案                              | 适合场景                                | 优点                                 | 局限                                                 |
| --------------------------------- | --------------------------------------- | ------------------------------------ | ---------------------------------------------------- |
| `a[href] + download`              | 静态资源、公开文件、同源文件            | 最简单，浏览器原生接管，内存占用低   | 难携带自定义请求头，错误处理弱，跨域与文件名控制受限 |
| `window.open` / `iframe` / `form` | 后端直接返回附件流，依赖 Cookie 登录态  | 对大文件友好，不需要前端缓存完整文件 | 难拿到进度与错误细节，交互控制较弱                   |
| `fetch` / `axios` + `Blob`        | 需要携带 Token、POST 下载、统一业务校验 | 控制力强，便于判错与自定义文件名     | 通常要先把文件完整读入内存，大文件压力明显           |
| `ReadableStream` 流式下载         | 大文件、需要进度、需要边读边处理        | 可按块消费数据，更适合长时间下载任务 | 实现复杂，真正边下边写磁盘依赖浏览器能力             |

## 选型建议

- 公开文件或简单附件下载，优先用 `a[href]`，让浏览器直接接管。
- 登录态下载且文件较大时，优先让后端返回 `Content-Disposition: attachment`，前端使用 `form`、`iframe` 或新窗口触发下载。
- 需要附带鉴权头、发起 `POST`、统一处理业务错误时，优先用 `fetch -> blob`。
- 文件很大，或者必须展示实时进度、避免一次性占满内存时，再使用流式方案。

## 最小示例

### `a[href] + download`

```html
<a href="/files/report.pdf" download="report.pdf">下载报告</a>
```

- 适合静态资源和无需额外鉴权头的文件。

### `fetch + Blob`

```js
async function downloadFile() {
  const res = await fetch('/api/export', {
    headers: {
      Authorization: 'Bearer token',
    },
  })

  if (!res.ok) {
    throw new Error('下载失败')
  }

  const blob = await res.blob()
  const url = URL.createObjectURL(blob)
  const a = document.createElement('a')
  a.href = url
  a.download = 'report.xlsx'
  a.click()
  URL.revokeObjectURL(url)
}
```

- 适合业务下载接口，但大文件场景要注意内存占用。

### `form` 触发附件下载

```html
<form action="/api/export" method="post" target="_blank">
  <input type="hidden" name="id" value="123" />
  <button type="submit">下载</button>
</form>
```

- 适合后端直接输出附件流，浏览器负责后续保存。

## 流式传输如何实现

前端流式下载的核心链路是：

1. 用 `fetch` 发起请求。
2. 从 `response.body` 读取 `ReadableStream`。
3. 通过 `getReader()` 按块消费数据。
4. 结合 `Content-Length` 计算进度。
5. 视场景决定是拼成 `Blob`，还是直接写入磁盘流。

### 基础流式读取

```js
async function streamDownload() {
  const res = await fetch('/api/download/large-file')

  if (!res.ok || !res.body) {
    throw new Error('流式下载失败')
  }

  const total = Number(res.headers.get('Content-Length')) || 0
  const reader = res.body.getReader()
  const chunks = []
  let loaded = 0

  while (true) {
    const { done, value } = await reader.read()
    if (done) break

    chunks.push(value)
    loaded += value.length

    if (total) {
      const percent = ((loaded / total) * 100).toFixed(2)
      console.log(`下载进度: ${percent}%`)
    }
  }

  const blob = new Blob(chunks)
  const url = URL.createObjectURL(blob)
  const a = document.createElement('a')
  a.href = url
  a.download = 'large-file.zip'
  a.click()
  URL.revokeObjectURL(url)
}
```

- 这个方案已经是“流式读取”，优点是可以拿到进度。
- 但如果最终仍然汇总成 `Blob`，大文件场景依然会占用较多内存。

### 直接写入磁盘流

```js
async function saveByStream() {
  const res = await fetch('/api/download/large-file')

  if (!res.ok || !res.body) {
    throw new Error('下载失败')
  }

  const handle = await window.showSaveFilePicker({
    suggestedName: 'large-file.zip',
  })
  const writable = await handle.createWritable()

  await res.body.pipeTo(writable)
}
```

- 这种方式不需要把完整文件先放进内存，更适合超大文件。
- 常见实现依赖 [File System Access API](https://developer.mozilla.org/en-US/docs/Web/API/File_System_Access_API)，兼容性不如传统下载方式。

## 服务端配合点

| 响应头 / 能力          | 作用                 | 说明                                            |
| ---------------------- | -------------------- | ----------------------------------------------- |
| `Content-Disposition`  | 告诉浏览器按附件下载 | 常见写法为 `attachment; filename="report.xlsx"` |
| `Content-Type`         | 声明文件 MIME 类型   | 便于浏览器和系统正确识别文件                    |
| `Content-Length`       | 提供总大小           | 前端可以据此计算百分比进度                      |
| `Accept-Ranges: bytes` | 支持范围请求         | 更利于断点续传、分段下载                        |
| 稳定鉴权方式           | 保证下载接口可访问   | 常见做法包括 Cookie、签名 URL、Bearer Token     |

- 如果服务端使用分块传输或动态生成文件，可能无法提供准确的 `Content-Length`。
- 这时前端仍然可以展示“已下载字节数”，但很难提供准确百分比。

## 实施建议

- 不要默认所有下载都走 `Blob`，这是大文件下载卡顿或崩溃的常见原因。
- 需要统一错误处理时，可以先校验响应头和业务状态，再决定是否进入下载流程。
- 导出类接口若预计文件很大，应优先评估“后端直出附件流”或“流式落盘”方案。
- 如果同时要求跨浏览器兼容与超大文件下载，通常需要同时准备“浏览器原生下载”和“增强流式下载”两套策略。
