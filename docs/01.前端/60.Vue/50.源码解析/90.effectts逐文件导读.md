# effect.ts 逐文件导读

## 阅读建议

- 这页不是替你逐行翻译源码，而是告诉你读 `effect.ts` 时每一段到底在解决什么问题。

## 核心目标

- 看完后能带着明确问题去读 `packages/reactivity/src/effect.ts`，而不是只看到一堆状态字段和分支判断。

## 先带着这几个问题进文件

1. effect 为什么需要单独的数据结构。
2. effect 执行时，怎么知道“当前是谁在收集依赖”。
3. effect 为什么需要 cleanup。
4. `stop` 为什么能让副作用彻底失效。
5. scheduler 为什么能接管 effect 的执行时机。

## 读文件时先抓主线

```text
创建 effect -> 运行 effect -> 记录当前 active effect -> track 收集依赖 -> cleanup 旧依赖 -> stop 终止响应
```

## 第一段先看什么

| 先看什么               | 想回答什么问题                |
| ---------------------- | ----------------------------- |
| effect 相关类或结构    | effect 自己需要保存哪些状态   |
| active effect 相关变量 | 当前正在执行的是哪一个 effect |
| run 方法               | effect 真正执行时做了哪些准备 |

## `run` 主线怎么理解

- `run()` 的重点不是“执行函数”这么简单。
- 它通常要做三件事：
  - 建立当前 active effect 上下文
  - 清理旧依赖，避免脏关联残留
  - 执行用户函数，让读取过程进入 `track`

## 为什么要有 active effect

- 因为 `track` 在收集依赖时，必须知道“当前正在执行的是谁”。
- 否则读取一个响应式属性时，根本不知道该把哪个 effect 放进依赖集合。

## cleanup 为什么是核心

| 不做 cleanup 会怎样          | cleanup 在解决什么                 |
| ---------------------------- | ---------------------------------- |
| effect 重新执行后旧依赖还在  | 移除过期依赖关系                   |
| 依赖集合越来越脏             | 保持依赖图与本轮真实读取结果一致   |
| 条件分支变化后仍被旧字段触发 | 让 effect 只订阅当前真正访问的依赖 |

## 最小示例

```ts
const state = reactive({ ok: true, text: 'hello' })

effect(() => {
  console.log(state.ok ? state.text : 'fallback')
})
```

- 这个例子最适合用来理解 cleanup：当 `ok` 变成 `false` 后，effect 不该再继续依赖 `text`。

## scheduler 在这个文件里怎么理解

- effect 不一定每次都自己立刻执行。
- 如果传了 scheduler，真正变化时可以先交给 scheduler 决定何时运行。
- 这就是后面 watcher、组件更新、job queue 能接进来的关键接口。

## `stop` 该怎么读

- `stop` 的重点不是“加一个标记位”。
- 真正关键的是：
  - 把 effect 从所有依赖集合里移除
  - 执行必要清理
  - 让后续变更不再触发它

## 读完 `effect.ts` 你应该得到什么

| 读完后应建立的认知             | 为什么重要                    |
| ------------------------------ | ----------------------------- |
| effect 是响应式系统的执行单元  | 后面 computed/watch 都基于它  |
| active effect 决定依赖收集对象 | 这是 `track` 成立的前提       |
| cleanup 保证依赖图不脏         | 否则条件分支和副作用会错乱    |
| scheduler 接出调度能力         | 这是 runtime 层能接上的关键口 |

## 接下来应该顺着读什么

1. `baseHandlers.ts`：读写代理时什么时候接到 `track` / `trigger`
2. `dep.ts`：依赖集合怎么组织
3. `computed.ts`：特殊 effect 怎么做缓存
4. `apiWatch.ts`：watcher 怎么建立在 effect 之上

## 常见误区

- 只盯 class 字段，不看它们在主线里解决什么问题。
- 看到 cleanup 就只想到清理副作用，忽略它还要清理依赖图。
- 把 scheduler 当成附加功能，没意识到它是 runtime 调度入口。
