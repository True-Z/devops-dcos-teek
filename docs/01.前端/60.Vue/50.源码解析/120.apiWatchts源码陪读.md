# apiWatch.ts 源码陪读

## 阅读建议

- 这页适合在你已经理解 effect 主线后再读，因为 `apiWatch.ts` 本质不是另起炉灶，而是在 effect 外包一层观察器能力。

## 核心目标

- 看完后能讲清：`watch` 和 `watchEffect` 在源码里是怎么统一到同一套观察逻辑上的，以及它们为什么又表现出不同能力。

## 先记住一句话

- `apiWatch.ts` 的核心不是“怎么监听”，而是“怎么把不同来源的依赖、不同回调时机、不同清理策略，包装成一套统一 watcher 行为”。

## 第一层：`watch` 和 `watchEffect` 为什么都能落到这里

- 因为它们背后都需要创建副作用执行单元。
- 区别不在于有没有 effect，而在于：
  - 依赖源是谁
  - 回调有没有新旧值
  - 是否自动收集依赖
  - flush 时机怎么控制

## 第二层：源码最先要处理什么

| 最先处理的事   | 目的                            |
| -------------- | ------------------------------- |
| 规范化 source  | 统一不同输入形式                |
| 生成 getter    | 让 watcher 知道到底该观察什么   |
| 准备 cleanup   | 让副作用失效时能正确清理        |
| 绑定 scheduler | 决定 watcher 回调在什么阶段执行 |

## source 为什么要先标准化

- 因为 `watch` 可以接很多形式：`ref`、getter、reactive 对象、数组来源。
- 源码必须先把这些不同输入收敛成统一 getter，后面 effect 才能稳定工作。

## `watch` 和 `watchEffect` 的核心分叉在哪里

| 能力          | 源码上的主要差异                    |
| ------------- | ----------------------------------- |
| `watch`       | 有明确 source，有回调，可拿新旧值   |
| `watchEffect` | 没有独立 source，执行时自动收集依赖 |

## 第三层：getter 在 watcher 里意味着什么

- getter 不是“顺手封装一下”。
- 它决定了 watcher 到底观察谁。
- 对 `watch(source, cb)` 来说，getter 是“取依赖源当前值”。
- 对 `watchEffect(fn)` 来说，getter 更接近“执行副作用本身，并在执行时收集依赖”。

## 第四层：新旧值为什么只有 `watch` 更强调

- 因为 `watch` 的语义本来就是“观察某个明确来源是否变化”。
- 所以它会保留上一次结果，再和这一次结果比较。
- `watchEffect` 更偏“只要依赖动了我就重跑”，它不强调新旧值对比。

## 第五层：cleanup 怎么接进 watcher

- watcher 不只是“变化后跑回调”，它往往还要处理过期副作用。
- 比如上一次请求还没结束，这一次已经切换依赖源了。
- 所以源码里会把 cleanup 和 watcher 生命周期绑在一起。

## 最小示例

```ts
watch(
  () => route.params.id,
  async (id, _, onCleanup) => {
    const controller = new AbortController()
    onCleanup(() => controller.abort())
  },
)
```

- 这个例子最适合用来理解：watcher 的价值不只是“能回调”，而是“能管理副作用失效”。

## 第六层：scheduler 和 flush 在这里怎么接入

- `apiWatch.ts` 不自己实现队列系统。
- 它主要做的是：根据 `flush` 配置，决定这个 watcher 回调交给哪个时机去执行。
- 真正的队列和执行顺序，还是落到 scheduler 那一层。

## 读 `apiWatch.ts` 时建议这样抓主线

1. 先看 source 如何被标准化成 getter。
2. 再看 `watch` 和 `watchEffect` 在 getter / callback 上如何分叉。
3. 再看 cleanup 如何注册和触发。
4. 最后看 scheduler / flush 如何把 watcher 接到 runtime 调度系统。

## 一句话串起来

```text
apiWatch.ts 负责把“依赖源 + 回调 + cleanup + flush 时机”包装成统一 watcher 行为
```

## 常见误区

- 以为 `watchEffect` 没有 source，就不走同一套主线。
- 只关注回调本身，忽略 source 标准化和 cleanup 才是 watcher 的关键包装层。
- 看到 `flush` 选项却没意识到它本质是在对接 scheduler。
