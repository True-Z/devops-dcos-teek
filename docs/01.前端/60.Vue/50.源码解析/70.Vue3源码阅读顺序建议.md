# Vue3 源码阅读顺序建议

## 阅读建议

- 这页重点不是列仓库目录，而是给你一个“先读什么、再读什么、每一步要带着什么问题去看”的阅读路线。

## 核心目标

- 看完后能带着地图进源码，不会一上来就在 runtime、compiler、reactivity 之间来回迷路。

## 最推荐的阅读顺序

1. 先读响应式主线，不急着看编译器。
2. 再读 `computed`、`watch`、`watchEffect` 这些基于 effect 的能力。
3. 再看调度器、job queue 和 flush 时机。
4. 然后看组件 render effect 如何接到更新流程。
5. 最后再去看 template -> render function -> patch。

## 为什么这样排

- 因为 Vue3 的很多能力，最后都能回到同一条主线：响应式依赖图 + effect + 调度更新。
- 如果一开始就看编译、patch、hydration，容易只看见流程细节，看不见核心骨架。

## 一张表看阅读路线

| 阶段 | 先理解什么                         | 目的                         |
| ---- | ---------------------------------- | ---------------------------- |
| 1    | `reactive`、`ref`、`effect`        | 建立响应式主线               |
| 2    | `computed`、`watch`、`watchEffect` | 理解派生值与副作用边界       |
| 3    | scheduler、job queue、flush        | 理解为什么更新不是同步乱跑   |
| 4    | 组件更新 effect                    | 把响应式和组件 render 接起来 |
| 5    | patch / diff / template compile    | 理解视图层最终如何更新       |

## 每一步要带着的问题

| 阶段 | 带着什么问题去看                   |
| ---- | ---------------------------------- |
| 1    | 依赖什么时候收集，变化什么时候触发 |
| 2    | 为什么三者都基于 effect 却职责不同 |
| 3    | 为什么 Vue 不立即同步执行所有更新  |
| 4    | 组件 render 为什么也能被当作副作用 |
| 5    | 数据变化最后为什么只是局部 patch   |

## 常见误区

- 一开始就盯具体源码文件细节，结果丢掉主线。
- 先啃编译器，反而不清楚运行时为什么要这样设计。
- 看了很多实现，却没把 `effect`、scheduler、组件更新这三块连起来。
