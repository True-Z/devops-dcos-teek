# Vue effect scope cleanup 与 stop 机制

## 阅读建议

- 这页重点不是只认识 `effectScope()` API，而是理解 Vue 为什么需要统一管理副作用的生命周期。

## 核心目标

- 看完后能说清：为什么副作用需要清理、`stop` 在停止什么、`effectScope` 为什么能把多个副作用纳入同一个生命周期边界。

## 最小主线

```text
create effect -> collect deps -> run side effect -> cleanup old deps / side effects -> stop when scope ends
```

## 为什么需要 cleanup

- 副作用不是只执行一次，它通常会重复运行。
- 如果每次重跑前不清理旧依赖、旧定时器、旧请求或旧监听，副作用就会不断叠加。
- 所以 cleanup 本质是在保证“旧的一轮副作用能正确退场”。

## `stop` 在停止什么

- 停止 effect 继续响应依赖变化。
- 断开它和依赖集合之间的关联。
- 执行必要的清理逻辑，避免后续继续触发。

## `effectScope` 在解决什么问题

| 问题                            | `effectScope` 的价值     |
| ------------------------------- | ------------------------ |
| 一个 composable 里有多个 effect | 可以统一收口和销毁       |
| 页面卸载时副作用分散            | 可以按 scope 一次性 stop |
| 生命周期边界不好管理            | 给副作用一个更清晰的归属 |

## 最小示例

```ts
const scope = effectScope()

scope.run(() => {
  watchEffect(() => {
    console.log(state.count)
  })
})

scope.stop()
```

- 这里真正重要的是：这个 scope 里创建出来的副作用，可以在一个边界上统一停止。

## cleanup 和 watcher 的关系

| 能力            | 更稳的理解方式                     |
| --------------- | ---------------------------------- |
| watcher cleanup | 当前一轮副作用失效时先执行清理     |
| `stop`          | 整个 watcher / effect 生命周期结束 |
| `effectScope`   | 给一组 effect 建一个统一容器       |

## 看源码时怎么抓主线

1. effect 运行时会记录自己依赖了哪些 dep。
2. 下一轮重跑前要把旧依赖关系清理掉，再重新收集。
3. `stop` 会把 effect 从这些 dep 中移除。
4. `effectScope` 再把多个 effect 的 stop 行为组织起来。

## 常见误区

- 以为 cleanup 只是为了清理请求，其实依赖关系本身也要清理。
- 以为 `stop` 只是“不再回调”，忽略它还要断开依赖关系。
- 在 composable 里创建很多 watcher，却不考虑这些 watcher 何时销毁。
