# scheduler.ts 源码陪读

## 阅读建议

- 这页重点不是把调度器实现逐行背下来，而是理解 Vue 为什么要维护一套 job queue，以及它怎样保证执行顺序、去重和 flush 时机。

## 核心目标

- 看完后能把 `scheduler.ts` 的主线说成一句话：把不同来源的更新 job 按规则入队、去重、排序，再在合适时机统一执行。

## 先记住一句话

- `scheduler.ts` 不是在决定“依赖谁”，而是在决定“已经确定要执行的这些 job，什么时候、按什么顺序执行”。

## 它接在主线的哪一段

```text
track -> trigger -> effect / watcher 被通知 -> scheduler 入队 -> flush jobs -> 组件更新 / watcher 回调
```

## 先带着这几个问题去看

1. 为什么不能每次变化都立刻同步执行 job。
2. 同一个 job 为什么需要去重。
3. 为什么 job 还要排序。
4. `pre` / 普通 / `post` 任务为什么要区分阶段。

## 第一层：queue 在解决什么问题

| 问题                 | scheduler 的解法                |
| -------------------- | ------------------------------- |
| 同一轮多次状态变更   | 合并更新                        |
| 同一 job 重复触发    | 去重                            |
| 父子组件顺序可能混乱 | 用 id / 标记维持稳定顺序        |
| DOM 时机不一致       | 区分 `pre`、主队列、`post` 阶段 |

## 第二层：为什么 job 不能无脑立刻执行

- 用户一次交互里可能连续改很多次状态。
- 如果每次都同步执行组件 render 或 watcher，重复 patch 会很多。
- 所以更合理的是：先把“需要执行”的 job 收集起来，再统一 flush。

## 第三层：去重要解决什么

- 一个组件更新 job 可能在同一轮被多次触发。
- 如果不去重，同一个组件会在一次事件里反复 render。
- 所以 scheduler 不是“多次通知就多次执行”，而是“本轮至少执行一次”。

## 第四层：排序为什么重要

| 为什么要排序                | 结果                         |
| --------------------------- | ---------------------------- |
| 父组件通常应先于子组件更新  | 避免子组件先跑导致状态不一致 |
| watcher / render 有阶段差异 | 保证读取 DOM 时机可预测      |
| 队列可能动态插入新 job      | 仍要维持整体执行顺序稳定     |

## 第五层：`pre` / 主队列 / `post` 怎么记

| 阶段   | 更适合什么                            |
| ------ | ------------------------------------- |
| `pre`  | 组件更新前要跑的 watcher 或前置副作用 |
| 主队列 | 组件 render effect、普通更新 job      |
| `post` | DOM 更新后再执行的副作用              |

## 最小示例

```ts
watch(source, callback, {
  flush: 'post',
})
```

- 这类配置最终不是自己实现队列，而是把回调交给 scheduler 进入对应阶段。

## 第六层：flush 过程在做什么

1. 取出当前待执行 job 队列。
2. 按规则执行 `pre` 任务和主任务。
3. 处理执行过程中新增的 job。
4. 执行 `post` 阶段回调。
5. 清理状态，准备下一轮调度。

## 读源码时建议这样抓

| 先看什么          | 想回答什么问题                |
| ----------------- | ----------------------------- |
| `queueJob`        | job 如何入队、如何去重        |
| flush 主函数      | 队列什么时候真正执行          |
| pre/post 队列相关 | 阶段是怎么区分和穿起来的      |
| 排序逻辑          | 为什么组件和 watcher 顺序稳定 |

## 常见误区

- 以为 scheduler 只是“异步执行一下”。
- 只看微任务，不看去重、排序、阶段划分这些真正核心点。
- 以为 watcher 的 `flush` 是 watcher 自己的实现细节，而不是在对接 scheduler。
