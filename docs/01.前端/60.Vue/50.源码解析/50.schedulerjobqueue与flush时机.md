# Vue scheduler job queue 与 flush 时机

## 阅读建议

- 这页重点不是记调度函数名，而是理解 Vue 为什么要把更新放进队列，以及队列在什么时候真正执行。

## 核心目标

- 看完后能说清：为什么 `trigger` 不等于立刻执行、job queue 在解决什么问题、`pre` / `post` / `sync` 的 flush 时机分别意味着什么。

## 最小主线

```text
trigger -> scheduler -> queue job -> flush jobs -> component update / watcher callback
```

## 为什么需要调度器

- 同一轮同步代码里，状态可能会连续改很多次。
- 如果每次 `trigger` 都立刻重新执行 render 或 watcher，重复计算和重复 patch 会很多。
- 所以 Vue 会把可合并的更新先放进队列，再统一 flush。

## 一张表看几个核心角色

| 角色        | 负责什么                         |
| ----------- | -------------------------------- |
| `trigger`   | 找到依赖并通知它们需要更新       |
| `scheduler` | 决定是立刻执行还是入队           |
| `job queue` | 去重、排序、批量执行待处理任务   |
| `flushJobs` | 在合适时机真正清空并执行任务队列 |

## job queue 在解决什么问题

| 问题               | 队列的价值                      |
| ------------------ | ------------------------------- |
| 连续多次状态修改   | 合并同一轮更新                  |
| 重复执行同一个 job | 去重，避免无意义重复            |
| 执行顺序混乱       | 保持组件和 watcher 执行顺序稳定 |

## flush 时机怎么理解

| flush 时机 | 更适合什么场景                           |
| ---------- | ---------------------------------------- |
| `pre`      | 组件更新前执行的 watcher 副作用          |
| `post`     | 组件 DOM 更新后再执行，需要读更新后 DOM  |
| `sync`     | 立即同步执行，适合少量必须立刻生效的逻辑 |

## 最小示例

```ts
watch(source, callback, {
  flush: 'post',
})
```

- 这类写法的重点是：回调不只是“变化后执行”，而是“变化后在什么阶段执行”。

## 处理顺序怎么记

1. 响应式数据变化。
2. `trigger` 找到相关 effect / watcher / component update。
3. 调度器判断是否入队。
4. 队列统一去重和排序。
5. flush 时真正执行 job。
6. `post` 类副作用在组件更新后执行。

## 看源码时最容易混的点

| 容易混的点         | 更稳的理解方式                  |
| ------------------ | ------------------------------- |
| 调度器很复杂       | 先抓住“合并更新”这个核心目的    |
| `flush` 很抽象     | 先当成“副作用执行阶段”          |
| 组件更新和 watcher | 二者都走调度，只是 job 类型不同 |
| `sync` 很方便      | 它绕过批量合并，不能无脑滥用    |

## 常见误区

- 以为 watcher 默认都是同步立刻执行。
- 看见队列就只想到异步，而忽略其核心是“批量去重与顺序控制”。
- 把所有需要 DOM 的 watcher 都写默认时机，结果读到的还是旧 DOM。
