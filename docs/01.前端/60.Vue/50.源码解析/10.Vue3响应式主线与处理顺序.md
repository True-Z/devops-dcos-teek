# Vue3 响应式主线与处理顺序

## 阅读建议

- 这页重点不是背源码文件名，而是先把 Vue3 响应式从“读数据”到“页面更新”的处理顺序串成一条主线。

## 核心目标

- 看完后能说清：依赖是何时收集的、更新是何时触发的、为什么不是每次改值都立刻重新渲染。

## 最小主线

```text
reactive/ref -> effect 读取 -> track 收集依赖 -> trigger 触发依赖 -> scheduler 调度 -> effect / component update 执行
```

## 先记住几个核心角色

| 角色        | 负责什么                             |
| ----------- | ------------------------------------ |
| `reactive`  | 把对象包装成 `Proxy` 代理            |
| `ref`       | 把单值包装成可跟踪容器               |
| `effect`    | 承载副作用函数，执行时收集依赖       |
| `track`     | 在读取时建立“属性 -> effect”依赖关系 |
| `trigger`   | 在写入时找到相关 effect 并触发       |
| `scheduler` | 决定立即执行还是进入任务队列合并更新 |

## 处理顺序怎么理解

1. 响应式对象被创建，但此时通常还没有依赖。
2. `effect`、`computed` getter 或组件 render 开始执行。
3. 执行过程中读取响应式数据，触发 `track`。
4. `track` 建立依赖映射：哪个 key 被哪个 effect 用到了。
5. 当响应式数据写入时，触发 `trigger`。
6. `trigger` 找到关联 effect，决定直接执行还是交给 `scheduler`。
7. 对组件更新和部分副作用，Vue 往往会放进调度队列，统一在合适时机刷新。

## 为什么 `trigger` 不等于立刻渲染

- 因为很多更新是同一轮事件循环里连续发生的。
- 如果每次修改都同步 render，一次表单输入就可能触发多轮重复渲染。
- 所以 Vue 会把可合并的 job 放进队列，在统一 flush 时执行。

## 一张表看常见 effect 来源

| 来源          | 本质上是什么                     |
| ------------- | -------------------------------- |
| 组件 render   | 一个会读取响应式状态的副作用函数 |
| `computed`    | 一个带缓存和脏标记的特殊 effect  |
| `watchEffect` | 一个自动收集依赖的副作用 effect  |
| `watch`       | 一个带明确依赖源和回调的观察逻辑 |

## 最小示例

```ts
const state = reactive({ count: 0 })

effect(() => {
  console.log(state.count)
})

state.count++
```

## 这个例子背后发生了什么

1. `effect` 执行时读取 `state.count`。
2. 读取触发 `track`，把当前 effect 收集到 `count` 的依赖集合。
3. `state.count++` 触发 `set`，进入 `trigger`。
4. `trigger` 找到这个 effect，再执行或调度它。

## 看源码时最容易乱的点

| 容易混的点                 | 更稳的理解方式                     |
| -------------------------- | ---------------------------------- |
| `reactive` 很重要          | 真正串起流程的是 `effect` 和依赖图 |
| `track` / `trigger` 很抽象 | 就当成“读时登记、写时通知”         |
| 组件更新很特殊             | 组件更新本质也是副作用，只是更复杂 |
| 调度器很多分支             | 先理解“合并更新”，再看细节时机     |

## 常见误区

- 以为 `reactive()` 一创建就已经“自动订阅”所有属性。
- 以为 `trigger` 之后就必然同步执行整棵组件树。
- 只盯着 `Proxy`，忽略真正的核心是依赖收集与调度。
