# computed.ts 源码陪读

## 阅读建议

- 这页重点不是只看 `computed` API 怎么用，而是理解源码里它为什么能做到“惰性求值 + 缓存 + 依赖联动”。

## 核心目标

- 看完后能讲清：`computed` 为什么本质上是特殊 effect，以及 dirty 标记和缓存为什么能成立。

## 先记住一句话

- `computed` 不是“自动计算一次然后存住”，而是“依赖变化时先标脏，真正有人读取时再重新计算”。

## 最小主线

```text
create computed -> getter effect 建立 -> 依赖变化时标脏 -> 读取 value 时刷新 -> 返回缓存结果
```

## 先带着这几个问题去看

1. `computed` 为什么不是每次依赖变化都立刻重新算。
2. dirty 标记到底在解决什么。
3. 缓存结果什么时候失效。
4. `computed` 为什么也是依赖图的一部分。

## 第一层：`computed` 为什么还是 effect

- 因为它也需要在 getter 执行时收集依赖。
- 只不过它和普通 effect 不一样：
  - 更强调返回值
  - 更强调缓存
  - 更强调惰性刷新

## 第二层：dirty 标记怎么理解

| 场景                   | 为什么需要 dirty       |
| ---------------------- | ---------------------- |
| 依赖变了但当前没人读值 | 不必立刻重算           |
| 下一次读取 `.value`    | 只有这时才真正重新求值 |
| 连续多次读取但依赖没变 | 直接复用缓存           |

## 第三层：为什么 `computed` 能缓存

- 因为它会保存上一次计算结果。
- 依赖没变时，读取 `.value` 不需要重新跑 getter。
- 只有当依赖变化把它标成 dirty，下一次读取才会刷新。

## 最小示例

```ts
const count = ref(1)

const doubled = computed(() => {
  console.log('recompute')
  return count.value * 2
})
```

- 如果连续多次读取 `doubled.value`，依赖没变时不会反复打印 `recompute`。

## 第四层：`computed` 为什么还能被别人依赖

- 因为 `computed` 自己虽然是派生值，但对外仍然表现成响应式来源。
- 模板、effect、watch 都可以依赖它。
- 所以它既是“依赖消费者”，也是“依赖生产者”。

## 第五层：读源码时先看什么

| 先看什么              | 想回答什么问题                   |
| --------------------- | -------------------------------- |
| computed 相关类或结构 | 保存值、dirty、dep 的位置在哪    |
| getter 执行入口       | 真正重新求值发生在什么时候       |
| 通知逻辑              | 依赖变化后它如何先标脏再通知外部 |
| 刷新逻辑              | 读取 `.value` 时如何决定是否重算 |

## 第六层：和 `watch` 最大的源码区别在哪

| 能力     | `computed`     | `watch`          |
| -------- | -------------- | ---------------- |
| 核心语义 | 派生值         | 变化后执行副作用 |
| 结果     | 对外暴露可读值 | 对外暴露回调执行 |
| 更新方式 | 标脏后按需刷新 | 变化后调度回调   |
| 缓存     | 强调缓存       | 不强调缓存       |

## 常见误区

- 以为 `computed` 每次依赖变化都会立刻重新计算。
- 把 `computed` 当 watcher 用，在 getter 里做副作用。
- 只看到缓存，不知道 dirty 才是缓存成立的关键条件。
