# effect.ts 源码陪读

## 阅读建议

- 这页适合你已经看过“逐文件导读”之后，再顺着主线把 `effect.ts` 真正拆开读一遍。

## 核心目标

- 看完后能把 `effect.ts` 里的核心逻辑按“创建、运行、收集、清理、停止、调度”六步讲清楚。

## 先记住一句话

- `effect.ts` 不是在做“响应式全部事情”，它主要在做一件事：定义副作用执行单元，以及这个执行单元如何和依赖系统协作。

## 第一层：为什么先有 effect

- Vue3 响应式不是“属性自己会更新页面”。
- 真正会被重新执行的是 effect。
- 组件 render、`computed`、`watchEffect`、`watch` 背后最终都要落到 effect 这一层。

## 第二层：effect 自己要保存什么

| 关注点         | 为什么要保存                       |
| -------------- | ---------------------------------- |
| 当前是否激活   | 避免 stop 后还继续参与依赖更新     |
| 已关联哪些 dep | 便于 cleanup 和 stop 时断开关系    |
| scheduler      | 把“何时执行”交给调度层决定         |
| 运行状态边界   | 避免递归、嵌套 effect 时上下文错乱 |

## 第三层：`run()` 进入时在做什么

1. 确认当前 effect 是否还能正常参与响应系统。
2. 把自己设置成当前 active effect。
3. 清理旧依赖关系。
4. 执行用户函数。
5. 执行过程中读取响应式数据，进入 `track`。
6. 运行结束后恢复上下文。

## 为什么运行前要 cleanup

- 因为 effect 每次重新执行后，访问到的依赖可能已经变了。
- 如果不先清理旧依赖，effect 就会继续订阅已经不再访问的字段。

## 最小分支示例

```ts
effect(() => {
  if (state.ok) {
    console.log(state.name)
  } else {
    console.log(state.age)
  }
})
```

- 这个例子里，`ok`、`name`、`age` 的依赖集合不会永远固定。
- 当分支切换时，旧依赖必须先被清掉，再按本轮访问结果重新建立。

## 第四层：active effect 为什么关键

- `track` 发生在 getter 一侧。
- getter 只知道“某个 key 被读取了”，不知道“是谁在读”。
- 所以必须通过 active effect 把“当前正在执行的副作用”传给 `track`。

## 第五层：scheduler 是怎样接进来的

- 默认情况下，依赖变化后 effect 可以直接重新执行。
- 但一旦存在 scheduler，effect 就不一定自己跑，而是把控制权交出去。
- 组件更新、watcher flush、job queue，本质都建立在这个“可调度 effect”能力上。

## 第六层：`stop()` 为什么不只是停回调

| `stop()` 做的事         | 目的                     |
| ----------------------- | ------------------------ |
| 把 effect 从 dep 中移除 | 后续变化不再触发它       |
| 标记自己不再活跃        | 避免继续参与响应式链路   |
| 执行清理逻辑            | 释放旧副作用和旧依赖关系 |

## 读源码时建议这样切分注意力

| 先看什么          | 再看什么                      |
| ----------------- | ----------------------------- |
| effect 的数据结构 | 字段分别服务于哪条主线        |
| `run()`           | active effect 与 cleanup      |
| `stop()`          | dep 清理与失活                |
| scheduler 接口    | runtime-core 如何接走执行控制 |

## 一句话串起来

```text
effect.ts 负责定义“谁执行、怎么执行、何时失效、如何被调度”
```

## 常见误区

- 以为 `track` / `trigger` 才是响应式核心，忽略 effect 才是执行主体。
- 只知道 effect 会收集依赖，不知道 cleanup 才保证依赖图长期正确。
- 读到 scheduler 时没接到 runtime-core，导致主线断掉。
