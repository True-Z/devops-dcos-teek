# Vue SSR Hydration 与客户端激活

## 阅读建议

- 这页重点不是只记住几个术语，而是理解“服务端先出 HTML，客户端为什么还要再接管一次”。

## 核心目标

- 理解 SSR、Hydration、客户端激活三者分别在做什么。

## 最小主线

```text
服务端生成 HTML -> 浏览器先看到内容 -> 客户端下载 JS -> Hydration 对齐 -> 事件与交互恢复
```

## SSR 是什么

- SSR 指服务端先把首屏 HTML 渲染出来再返回给浏览器。
- 这样浏览器在 JS 还没完全执行前，也能更早看到页面内容。

## 为什么还需要 Hydration

- 因为服务端返回的 HTML 只有结果，没有真正把客户端组件实例和事件系统接起来。
- Hydration 的作用就是让客户端运行时“接管”这份已存在的 DOM，而不是整棵树重新创建。

## 客户端激活在做什么

- 可以把客户端激活理解成：Vue 在浏览器端把已有 DOM、组件状态、事件监听重新对齐并挂接完成。
- 激活完成后，页面才真正进入完整可交互状态。

## 为什么会问 Hydration mismatch

- 因为如果服务端生成的内容和客户端首次渲染结果不一致，Hydration 就可能对不上。
- 常见原因：
  - 服务端和客户端使用了不同随机值
  - 直接依赖浏览器环境对象
  - 时间、地区、设备相关结果不一致

## 最小示例

```text
SSR 负责更早展示内容
Hydration 负责接管现有 DOM
激活完成后才具备完整交互能力
```

## SSR 的价值和代价

| 维度     | 价值               | 代价                       |
| -------- | ------------------ | -------------------------- |
| 首屏体验 | 更早看到内容       | 服务端渲染成本上升         |
| SEO      | 更利于爬虫获取内容 | 运行链路更复杂             |
| 交互恢复 | 可在激活后平滑接管 | Hydration 不一致要额外处理 |

## 常见误区

- 以为 SSR 就等于页面已经完全可交互。
- 以为 Hydration 是“重新渲染一遍页面”。
- 直接在服务端渲染流程里使用 `window`、`document`。
