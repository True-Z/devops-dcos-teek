# Vue 通用组件抽象策略

## 阅读建议

- 这页重点不是“抽得越多越好”，而是判断什么时候该抽成通用组件，什么时候应留在业务内部。

## 核心目标

- 理解通用组件抽象的目标，是减少重复实现和认知分裂，而不是制造一层新的复杂度。

## 什么样的能力适合抽象

| 场景                       | 是否适合抽象 |
| -------------------------- | ------------ |
| 多页面重复出现的交互壳子   | 适合         |
| 输入输出边界稳定的能力     | 适合         |
| 强依赖单一业务字段的流程   | 未必适合     |
| 只出现一次且变化频繁的写法 | 不适合       |

## 抽象前先看三件事

1. 复用是不是已经在多个页面真实出现。
2. 输入输出边界是不是能稳定命名。
3. 抽象后调用方是不是会更简单，而不是更绕。

## 推荐抽象路径

| 路径       | 更适合什么问题               |
| ---------- | ---------------------------- |
| 工具函数   | 纯数据转换、格式化、映射逻辑 |
| composable | 状态、副作用、交互流程复用   |
| 基础组件   | 视觉壳子和统一交互约定       |
| 复合组件   | 稳定页面片段和高频组合场景   |

## 状态归属怎么判断

- 通用组件优先只持有自身必要的局部状态，比如展开、聚焦、临时输入值。
- 列表数据、筛选条件、接口请求结果这类业务状态，通常应留在页面或 store。

## 最小示例

```vue
<BaseTable :columns="columns" :data-source="list" :loading="loading">
  <template #actions="{ row }">
    <button @click="edit(row)">编辑</button>
  </template>
</BaseTable>
```

- 表格壳子可以抽通用，但行操作、业务按钮和权限差异通过扩展位留给页面决定。

## 常见误区

- 一发现重复就直接抽，结果把偶然相似当成稳定共性。
- 通用组件内部偷偷发请求，调用方却无法感知副作用。
- 为了兼容历史场景不断加布尔开关，最后 props 爆炸。
- 把页面编排问题强塞给组件内部处理。
