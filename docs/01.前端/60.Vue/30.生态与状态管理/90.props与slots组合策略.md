# Vue props 与 slots 组合策略

## 阅读建议

- 这页重点不是区分两个 API 名词，而是判断组件能力应该通过配置传入，还是通过内容扩展传入。

## 核心目标

- 理解 `props` 解决的是可枚举配置问题，`slots` 解决的是结构与内容扩展问题。

## 一张表看边界

| 方式  | 更适合承载什么                     |
| ----- | ---------------------------------- |
| props | 状态、枚举、文案、尺寸、开关       |
| slots | 自定义结构、复杂内容、局部渲染差异 |
| emits | 交互结果和状态变更通知             |

## 什么时候优先用 props

- 能被稳定枚举的能力优先走 `props`，例如 `size`、`type`、`disabled`、`loading`。
- 调用方只需要改配置，不需要接管内部结构时，也优先走 `props`。

## 什么时候优先用 slots

- 当调用方需要定制头部、单元格、页脚、空态这类局部结构时，更适合用 `slots`。
- 当组件需要做“外部提供内容，内部负责布局”的封装时，更适合用 `slots`。

## 推荐组合主线

1. 稳定共性走 `props`。
2. 局部差异走 `slots`。
3. 用户交互结果通过 `emits` 往外通知。
4. 不要把所有扩展都压成一个万能对象。

## 最小示例

```vue
<DataPanel title="用户列表" :loading="loading">
  <template #toolbar>
    <button @click="refresh">刷新</button>
  </template>

  <template #default>
    <UserTable :list="list" />
  </template>

  <template #empty>
    暂无数据
  </template>
</DataPanel>
```

- 这里 `title`、`loading` 是稳定配置，`toolbar`、`default`、`empty` 是局部扩展位。

## 怎么避免 props 爆炸

| 信号                   | 说明                         |
| ---------------------- | ---------------------------- |
| 出现大量互斥布尔开关   | 说明配置边界可能已经失控     |
| 调用方想传整段模板内容 | 说明更适合改成 slots         |
| props 名称越来越业务化 | 说明组件可能该下沉回业务层   |
| 一个对象承载十几种能力 | 说明需要重新拆分接口或扩展位 |

## 常见误区

- 明明是结构扩展问题，却用一堆 `showXxx`、`renderXxx` props 硬顶。
- 明明只是简单枚举配置，却用 slots 让调用方重复写模板。
- 组件把 `props`、`slots`、`emits` 边界混在一起，导致维护成本持续升高。
