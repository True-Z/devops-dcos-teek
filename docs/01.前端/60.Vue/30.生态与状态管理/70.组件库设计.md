# Vue 组件库设计

## 阅读建议

- 这页重点不是讨论某个 UI 框架，而是理解团队为什么要做组件库，以及组件库应该分到哪一层。

## 核心目标

- 理解组件库设计的本质，是把重复 UI 能力、交互约定和视觉一致性沉淀成稳定资产。

## 组件库常见分层

| 层级          | 更适合承载什么                         |
| ------------- | -------------------------------------- |
| Design Tokens | 颜色、间距、字号、圆角、阴影           |
| 基础组件      | Button、Input、Modal、Table 等通用壳子 |
| 复合组件      | SearchForm、DataTable、DialogForm      |
| 业务组件      | 强依赖业务字段、接口和流程的组件       |

## 为什么先分层再写组件

- 因为很多“组件复用失败”并不是代码问题，而是一开始就把视觉规则、交互规则和业务规则混在了一起。
- 分层越清晰，组件越容易复用、替换和升级。

## 设计主线

1. 先确定 Design Tokens 和主题能力。
2. 再定义基础组件的视觉与交互约定。
3. 复合组件只封装稳定组合，不提前吃掉业务差异。
4. 业务组件优先放业务域内部，成熟后再考虑上收。

## API 设计关注点

| 关注点   | 说明                                    |
| -------- | --------------------------------------- |
| 稳定性   | 已发布 API 尽量向后兼容                 |
| 一致性   | 命名、事件、状态枚举保持统一            |
| 可扩展性 | 留出 slots、render 扩展位，而非堆 props |
| 可测试性 | 样式状态、交互状态、禁用态可验证        |

## 最小示例

```ts
type ButtonVariant = 'primary' | 'secondary' | 'danger'
type ButtonSize = 'sm' | 'md' | 'lg'
```

- 组件库 API 先统一“变体”和“尺寸”这类稳定语义，再考虑业务页面怎么组合使用。

## 常见误区

- 还没有复用场景，就过早建设大而全组件库。
- 基础组件直接感知接口字段和业务状态，导致无法跨项目复用。
- 一个组件内部塞满特殊分支，最后没人敢升级。
- 只有代码，没有文档、示例和变更约定。
