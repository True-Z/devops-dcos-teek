# Vue 组合式 API 与 Composables 设计

## 阅读建议

- 这页重点不是罗列 API，而是理解什么时候该抽 composable，什么时候不该抽。

## 核心目标

- 理解 Composition API 为什么能让逻辑按关注点组织，而不是被 options 分散。

## Composition API 解决什么问题

- 让相关逻辑可以按功能聚合，而不是被 `data`、`methods`、`computed`、`watch` 分散在不同区域。
- 当页面复杂时，这种组织方式更利于复用与拆分。

## 什么是 composable

- composable 本质上是一个封装了响应式状态和副作用逻辑的函数。
- 它通常以 `useXxx` 命名，用来复用某类业务能力。

```ts
import { ref, onMounted, onUnmounted } from 'vue'

export function useWindowWidth() {
  const width = ref(window.innerWidth)

  const handler = () => {
    width.value = window.innerWidth
  }

  onMounted(() => window.addEventListener('resize', handler))
  onUnmounted(() => window.removeEventListener('resize', handler))

  return { width }
}
```

## 什么时候该抽 composable

| 场景                             | 是否适合抽离 |
| -------------------------------- | ------------ |
| 多个页面重复使用的逻辑           | 适合         |
| 需要统一副作用管理               | 适合         |
| 只在单个组件里出现一次的简单逻辑 | 未必需要     |
| 过度拆分导致理解成本上升         | 不适合       |

## 设计 composable 的建议

1. 输入输出边界清晰
2. 副作用成对清理
3. 不把无关业务硬塞进同一个 `useXxx`
4. 命名反映能力，而不是实现细节

## 常见误区

- 为了“看起来像 Vue3 写法”把所有逻辑都拆成 composable。
- composable 内部偷偷做太多副作用，调用方却不知道。
- 一个 composable 既管请求、又管弹窗、又管路由，边界失控。
