# Vue 组件事件设计与 emits 契约

## 阅读建议

- 这页重点不是记事件名写法，而是让组件事件具备稳定语义、可预测时机和清晰责任边界。

## 核心目标

- 理解 `emits` 的价值，不只是声明事件，而是把组件对外输出能力收敛成可维护契约。

## 组件事件常见分类

| 类型         | 常见例子                      |
| ------------ | ----------------------------- |
| 值更新事件   | `update:modelValue`           |
| 交互通知事件 | `change`、`select`、`confirm` |
| 生命周期事件 | `open`、`close`、`loaded`     |
| 失败反馈事件 | `error`、`retry`              |

## 设计事件时先想什么

1. 这个事件表达的是状态变化，还是用户动作。
2. 事件触发时机是不是稳定可预测。
3. 事件参数是不是只暴露必要信息。
4. 同类组件之间命名能否保持一致。

## 推荐设计主线

- 值同步事件和业务动作事件分开设计。
- 不要让一个事件同时承载多个语义。
- 优先让调用方通过事件感知结果，而不是窥探组件内部状态。

## 最小示例

```ts
const emit = defineEmits<{
  'update:modelValue': [value: string]
  change: [value: string]
  clear: []
}>()
```

- `update:modelValue` 负责同步值，`change` 负责表达结果已确认，语义分开后更易维护。

## 一张表看常见边界

| 问题                 | 更推荐的做法                 |
| -------------------- | ---------------------------- |
| 值变化和提交混在一起 | 拆成独立事件                 |
| 事件名过于业务化     | 下沉回业务组件，不留在基础层 |
| 参数过大             | 只传必要字段，避免整对象     |
| 事件时机不稳定       | 明确在输入时、确认时或关闭时 |

## 常见误区

- 一个 `change` 事件同时代表输入中、选择完成和提交成功。
- 事件名随手写，导致同类组件行为不一致。
- 把内部全部状态打包原样抛给外部，造成调用方强耦合。
