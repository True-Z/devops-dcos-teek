# Vue provide inject 使用边界与依赖注入策略

## 阅读建议

- 这页重点不是会不会写 `provide` / `inject`，而是判断它适不适合当前这条状态链路。

## 核心目标

- 理解 `provide` / `inject` 适合解决明确上下文下的跨层传递问题，但不适合充当通用全局状态管理。

## 一张表看适用边界

| 场景                   | 是否适合 `provide/inject` |
| ---------------------- | ------------------------- |
| 表单组共享上下文       | 适合                      |
| 主题、国际化局部上下文 | 适合                      |
| 组件树内部服务对象     | 适合                      |
| 跨页面全局共享状态     | 不适合                    |
| 团队难以追踪的数据流   | 不适合                    |

## 为什么它常被误用

- 因为它看起来能“绕过 props 逐层传递”，所以容易被拿来解决所有层级传值问题。
- 但一旦注入链路过长、依赖关系不透明，排查成本会迅速升高。

## 推荐使用主线

1. 先判断是不是局部组件树上下文。
2. 再判断调用方是否明确知道依赖来源。
3. 只注入稳定能力或稳定上下文，不注入四处漂移的业务状态。
4. 需要全局共享和 DevTools 可追踪能力时，优先用 store。

## 最小示例

```ts
provide('formContext', {
  disabled,
  labelWidth,
})
```

- 这种写法更适合在 `Form` 和 `FormItem` 之间共享稳定上下文，而不是在页面里随意跨层传业务对象。

## 设计建议

| 关注点   | 说明                             |
| -------- | -------------------------------- |
| 命名     | 注入 key 语义清晰，避免过于泛化  |
| 边界     | 只在明确组件树内部使用           |
| 可维护性 | 让使用方知道依赖来自哪里         |
| 替代方案 | 父子优先 `props`，全局优先 store |

## 常见误区

- 把 `provide/inject` 当成 Pinia 替代品。
- 注入一个巨大对象，导致依赖边界完全模糊。
- 组件离开特定父层就无法工作，却没有任何文档说明。
