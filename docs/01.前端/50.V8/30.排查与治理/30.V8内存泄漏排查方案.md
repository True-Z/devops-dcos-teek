# V8 内存泄漏排查方案

## 模块定位

- 这页更偏“问题排查方案”，适合在页面长期运行卡顿、内存持续上涨时回查。

## 典型现象

- 页面使用时间越长越卡。
- 页面切换后内存不回落。
- 间歇性卡顿与 GC 频繁触发并存。

## 常见泄漏源

| 泄漏源         | 场景             | 处理方向             |
| -------------- | ---------------- | -------------------- |
| 闭包长期引用   | 回调持有大对象   | 缩短引用链，及时置空 |
| 事件监听未释放 | 页面销毁后仍监听 | 生命周期结束时解绑   |
| 定时器未清理   | 轮询、心跳任务   | 销毁时清理 timer     |
| 缓存无上限     | 本地缓存无限增长 | 设计过期与容量策略   |

## 最小示例

### 事件监听未释放

```js
function bindResize() {
  const handler = () => console.log('resize')
  window.addEventListener('resize', handler)

  return () => window.removeEventListener('resize', handler)
}
```

- 关键点不是“绑定”，而是要保留解绑入口。

### 定时器未清理

```js
const timer = setInterval(() => {
  fetchStatus()
}, 5000)

clearInterval(timer)
```

- 轮询类逻辑如果没有清理，页面离开后仍可能持续占用资源。

### 闭包持有大对象

```js
function createCache(data) {
  return function getItem(key) {
    return data[key]
  }
}
```

- 如果 `data` 很大且长期被闭包引用，就可能导致内存长期无法释放。

## 排查顺序

1. 复现问题并记录操作路径。
2. 观察内存趋势与 GC 行为。
3. 对比快照，定位持续增长对象。
4. 回溯引用链，找到未释放根因。
5. 修复后做回归验证。

## 实施建议

- 给高风险模块建立“销毁清单”（监听、定时器、订阅、缓存）。
- 对长期运行页面做周期性内存巡检。
- 将内存问题纳入上线前检查项；需要工具操作时可继续看 [Chrome DevTools Memory](https://developer.chrome.com/docs/devtools/memory/)。
