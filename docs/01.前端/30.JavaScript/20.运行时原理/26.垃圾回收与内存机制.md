# JavaScript 垃圾回收与内存机制

## 核心目标

- 理解对象为什么会被回收、为什么会内存泄漏、为什么有时会卡顿。

## 核心概念速查

| 概念          | 含义                       | 关注点           |
| ------------- | -------------------------- | ---------------- |
| 可达性        | 还能否从根对象访问到某对象 | 垃圾回收判断基础 |
| 新生代/老生代 | 不同生命周期对象的分区     | 回收频率与停顿   |
| 内存泄漏      | 本该释放却仍被引用         | 页面越用越卡     |

## 最小示例

```js
let cache = { list: new Array(10000).fill('x') }
cache = null
```

- 当对象不再可达时，才有机会被垃圾回收器回收。

## 常见泄漏源

- 闭包长期持有大对象
- 事件监听未解绑
- 定时器未清理
- 全局缓存无上限

## 面试短答

### 垃圾回收是怎么判断对象该不该回收的

- 核心判断标准不是“你还想不想用”，而是“这个对象是否仍然可达”。
- 只要一个对象已经无法从根对象继续访问，垃圾回收器就认为它可以被回收。

### 为什么明明写了 `delete` 或赋值 `null`，内存还是没立刻降下去

- `delete` 或置空只是减少引用，不等于立即触发回收。
- 是否回收、何时回收，要由垃圾回收器按自己的时机决定。
- 所以更准确的说法是：对象“变得可回收”，而不是“被你手动立即释放”。

### 为什么垃圾回收会导致卡顿

- 垃圾回收虽然是自动的，但并不是零成本。
- 当对象很多、存活对象复杂、老生代回收开销变大时，就可能造成停顿。
- 前端感知通常表现为：滚动卡顿、交互延迟、页面越用越慢。

## 常见追问

| 问题             | 回答抓手                             |
| ---------------- | ------------------------------------ |
| 为什么会内存泄漏 | 本该不可达的对象仍被引用             |
| 为什么会卡       | 主线程有 GC 停顿或对象管理成本过高   |
| 怎么避免         | 控制对象生命周期，及时解绑和清理     |
| 怎么排查         | 看堆快照、分配时间线、监听器和定时器 |

## Chrome DevTools 排查路径

### 1. 先判断是不是“越用越涨”

- 打开 Chrome DevTools -> `Memory`。
- 连续做几轮相同操作，比如打开弹窗、切换页面、重复渲染列表。
- 如果每一轮结束后堆内存基线都明显抬高，就要怀疑有泄漏。

### 2. 看 Heap Snapshot

- 在 `Memory` 面板选择 `Heap snapshot`。
- 先拍一份初始快照，再执行操作，再拍第二份快照。
- 重点看：
  - `Detached DOM tree`
  - 大数组、大对象
  - 被闭包长期持有的数据
  - 数量异常增长的构造函数实例

### 3. 看 Allocation instrumentation on timeline

- 这个模式更适合看“操作过程中到底分配了什么”。
- 当你做一次交互后，观察是否有对象不断分配但没有回落。
- 适合定位动画、轮询、滚动监听、频繁渲染类问题。

### 4. 结合 Elements / Event Listeners 排查

- 如果怀疑 DOM 泄漏，去 `Elements` 看节点是否已经脱离文档但仍被引用。
- 如果怀疑监听器没清理，检查事件绑定是否随着组件反复挂载不断叠加。
- 如果怀疑定时器问题，检查轮询、`setInterval`、长生命周期回调是否被忘记清除。

### 5. 最后回到代码定位引用链

- 真正要找的不是“哪个对象大”，而是“谁还在引用它”。
- 顺着快照里的 retaining path 去看，通常能定位到：
  - 全局缓存
  - 闭包环境
  - 未解绑监听器
  - 定时器回调
  - 框架组件的残留引用

## 最小排查清单

- 页面卸载时是否解绑监听器
- 定时器、订阅、轮询是否清理
- 缓存是否有上限与淘汰策略
- 闭包是否长期持有大对象或 DOM
- 大列表、图表、编辑器实例是否正确销毁

## 常见误区

- 以为手动 `delete` 就等于内存一定立刻释放。
- 只看代码逻辑对不对，不看对象生命周期。
- 认为垃圾回收是“完全自动，不需要关心”。
