# JavaScript 场景应用方案

## 阅读建议

- 这页更适合按场景查阅，不适合一次读完所有方案实现。
- 先看“适用边界”和“推荐顺序”，再决定要不要深入到具体实现。
- 这页更像场景入口页：先帮你排除不合适的方案，再给最小实现与常见坑。

## 场景选型总表

| 场景                | 优先方案                                                                              | 先判断什么                                   |
| ------------------- | ------------------------------------------------------------------------------------- | -------------------------------------------- |
| 跨标签页/上下文通信 | 同源广播优先 `BroadcastChannel`，定向跨源优先 `postMessage`，服务端中转用 `WebSocket` | 是否同源、是否已持有窗口引用、是否需要服务端 |
| 大屏适配            | 优先 `vw/vh`，允许留边且追求低改造成本时用 `scale`                                    | 是否允许留白、热区偏移、图表适配成本         |

## 跨标签页/上下文通信

- 这个场景常见于：单点登录状态同步、多个后台标签页共享通知、弹窗与主页面通信。
- 方案选择不能只看“能不能传”，还要看是否同源、是否持有目标窗口引用、是否需要服务端参与。

### 适用边界

| 判断维度         | 关键问题                                  |
| ---------------- | ----------------------------------------- |
| 是否同源         | 不同标签页是否同协议、同域名、同端口      |
| 是否持有窗口引用 | 是否能拿到 `window.open()` 或 iframe 引用 |
| 是否需要广播     | 是定向发给一个页面，还是多个页面同时接收  |
| 是否需要服务端   | 是否需要跨设备、跨浏览器或离线后重连      |
| 浏览器兼容       | 是否必须覆盖旧浏览器                      |

### 场景选型表

| 目标               | 优先方案                  | 说明                           |
| ------------------ | ------------------------- | ------------------------------ |
| 同源多标签页广播   | `BroadcastChannel`        | API 简洁，天然适合广播         |
| 已持有目标窗口引用 | `postMessage`             | 可跨源，但前提是拿得到目标窗口 |
| 需兼容较广浏览器   | `storage` / `postMessage` | 心智负担低，兼容性相对更稳     |
| 需服务端统一中转   | `WebSocket`               | 适合跨端、跨设备、多人同步     |
| 需共享后台线程能力 | `SharedWorker`            | 能力强，但兼容性要单独评估     |

### 推荐顺序

1. 同源且需要广播：优先 `BroadcastChannel`
2. 已持有目标窗口/iframe 引用：优先 `postMessage`
3. 只做低频状态同步且兼容优先：可用 `storage`
4. 需要跨端或服务端中转：用 `WebSocket`
5. 只有在明确需要共享线程能力时，才考虑 `SharedWorker`

| 方案                  | 优点                          | 缺点                                            |
| --------------------- | :---------------------------- | :---------------------------------------------- |
| postMessage           | 1. 兼容性好<br />2. 实现简单  | 需要获取对应标签页的引用                        |
| Storage Event         | 1. 兼容性好<br />2. 实现简单  | 1. 需同源<br />2. 存储大小限制                  |
| Shared Worker         | 后台线程运行                  | 1. 需同源<br />2. 需考虑兼容性                  |
| Message Channel       | 相较于 postMessage 简化了使用 | 1. 需提前传递 channel port<br />2. 需考虑兼容性 |
| **Broadcast Channel** | 实现简单，使用方便            | 1. 需同源<br />2. 需考虑兼容性                  |
| **Web Socket**        | 使用方便                      | 1. 需要服务器端支持<br />2. 网络通信消耗        |
| **...**               |                               |                                                 |

### 1. postMessage

**window.postMessage()** 方法可以安全地实现跨源通信。

- 适合“主页面与弹窗”“页面与 iframe”的定向通信。
- 重点不是它能不能跨源，而是你是否已经拿到目标窗口引用。

```js
// page one
const popup = window.open(...popup details...);
popup.postMessage('message', targetOrigin, [transfer])

// page two
window.addEventListener('message', (e) => {
  // 校验信息来源
  if (e.origin !== targetOrigin) {
    return
  }
  // => event.data
})
```

### 2. Storage Event

作为 Web Storage API 的接口，**Storage** 提供了访问特定域名下的会话存储或本地存储的功能，例如，可以添加、修改或删除存储的数据项。

- 适合同源页面之间做低频状态同步，比如“退出登录”“主题切换”。
- 不适合高频消息流，也不适合复杂结构广播。

```js
// page one
localStorage.setItem('message', 'data')

// page two
window.addEventListener('storage', (e) => {
  if (e.key === 'message') {
    // => event.data
  }
})
```

### 3. Shared Worker

**SharedWorker** 接口代表一种特定类型的 worker，可以从几个浏览上下文中访问，例如几个窗口、iframe 或其他 worker。

- 适合多个页面共享同一份后台计算或连接资源。
- 只有在你明确知道自己要复用后台线程能力时才值得引入。

```js
// page one
const worker = new SharedWorker('worker.js')
worker.port.postMessage('message')

// page two
const worker = new SharedWorker('worker.js')
worker.port.addEventListener('message', (e) => {
  // => e.data
})
worker.port.start()

// worker.js
self.addEventListener('connect', (e) => {
  const port = e.ports[0]
  port.addEventListener('message', (event) => {
    port.postMessage(event.data)
  })
})
```

> [!tip]
>
> 使用 `addEventListener` 监听 message 需手动调用 `start()` 。

### 4. Message Channel

**Channel Messaging API** 的 MessageChannel 接口允许我们创建一个新的消息通道，并通过它的两个 MessagePort 属性发送数据。

- 它更像“专用管道”，适合已经建立连接关系后的双向通信。
- 一般不会作为跨标签页通信的第一选择，更多是做能力补充。

```js
// page one
const channel = new MessageChannel()
const popup = window.open(...popup details...);
popup.postMessage(message, targetOrigin, [channel.port2])
channel.port1.addEventListener('message', (e) => {
	// => e.data
})
channel.port1.start()

// page two
window.addEventListener("message", (e) => {
  // 校验信息来源
  if (e.origin !== targetOrigin) {
    return
  }
  const messagePort = e.ports?.[0]
  messagePort.postMessage('message')
})
```

> [!tip]
>
> 使用 `addEventListener` 注册事件时需显式调用 `start()` 。

### 5. Broadcast Channel

**BroadcastChannel** 接口表示**给定源**的任何浏览上下文都可以订阅的命名频道。它允许**同源**的不同浏览器窗口、标签页、frame 或者 iframe 下的同文档之间相互通信。消息通过 message 事件进行广播，该事件在侦听该频道的所有 BroadcastChannel 对象上触发，发送消息的对象除外。

- 同源广播场景下通常是首选方案。
- 心智模型简单，但要注意浏览器兼容性与资源清理。

```js
// page one
const channel = new BroadcastChannel('channelName')
channel.postMessage('message')

// page two
const channel = new BroadcastChannel('channelName')
channel.addEventListener('message', (e) => {
  // => e.data
})
```

### 6. Web Socket

**WebSocket** 对象提供了用于创建和管理 WebSocket 连接，以及可以通过该连接发送和接收数据的 API。

- 它解决的是“服务端中转的实时通信”，不是简单替代 `BroadcastChannel` 或 `postMessage`。
- 当你需要跨设备、跨浏览器、跨登录态同步时，它的价值才真正体现出来。

```js
// page one
const socket = new WebSocket('ws://localhost:8080')
socket.addEventListener('open', (e) => {
  socket.send('message')
})

// page two
const socket = new WebSocket('ws://localhost:8080')
socket.addEventListener('message', (e) => {
  // => e.data
})
```

### 常见坑

- `postMessage` 必须校验 `origin`，不能只收不验。
- `storage` 事件不会在当前触发 `setItem` 的页面自己触发。
- `BroadcastChannel`、`SharedWorker`、`WebSocket` 用完要关闭，避免资源泄漏。
- `WebSocket` 需要额外处理重连、心跳、断线恢复，不只是“能连上”就结束。

## 大屏适配

- 这个场景的核心不是“能不能缩放”，而是“视觉还原、交互热区、改造成本”三者怎么取舍。

### 适用边界

| 判断维度     | 关键问题                               |
| ------------ | -------------------------------------- |
| 是否允许留白 | 屏幕比例与设计稿不一致时是否能接受空边 |
| 是否允许偏移 | 缩放后点击热区、拖拽位置能否容忍偏差   |
| 图表复杂度   | 是否有大量图表、绝对定位、拖拽组件     |
| 维护成本     | 是快速落地还是长期响应式维护           |

### 推荐顺序

1. 新页面或长期维护页面：优先 `vw/vh`
2. 存量大屏项目且允许留边：可用 `scale`
3. 需要按根字号驱动整站比例时：再考虑 `rem`

| 方案      | 优点                                                                                                  | 缺点                                                                                                                                                               |
| --------- | :---------------------------------------------------------------------------------------------------- | :----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| scale     | 代码量少，适配简单，无须其他操作                                                                      | 1. 因为是根据 UI 稿等比缩放，当大屏跟 UI 稿的比例不一样时，会出现周边留白情况<br/>2. 当缩放比例过大时，字体会有一点点模糊<br />3. 当缩放比例过大时，事件热区会偏移 |
| rem       | 可以动态计算图表的宽高，字体等，灵活性较高                                                            | 1. 因为是根据 UI 稿等比缩放，当大屏跟 UI 稿的比例不一样时，会出现周边留白情况<br/>2. 图表需要单个做字体、间距、位移的适配                                          |
| **vw/vh** | 1. 可以动态计算图表的宽高，字体等，灵活性较高<br/>2. 当屏幕比例跟 ui 稿不一致时，不会出现两边留白情况 | 图表需要单个做字体、间距、位移的适配                                                                                                                               |
| **...**   |                                                                                                       |                                                                                                                                                                    |

### 1. scale

- 优点是改造快，适合快速还原设计稿。
- 缺点也很明确：留白、模糊、热区偏移，都是后续维护成本。

- 当**视口宽高比 < 设计稿宽高比**，缩放的比例是视口宽度 / 设计稿宽度，**适配宽度**。

- 当**视口宽高比 > 设计稿宽高比**，缩放的比例是视口高度 / 设计稿高度，**适配高度**。

```js
const scale =
  document.documentElement.clientWidth / document.documentElement.clientHeight < designDraftWidth / designDraftHeight
    ? document.documentElement.clientWidth / designDraftWidth
    : document.documentElement.clientHeight / designDraftHeight
// 适配短边
document.querySelector('#layout').style.transform = `scale(${scale})`
```

```css
#layout {
  transform-origin: left top;
}
```

### 2. rem

动态获取视口宽度并设置 html font-size 为视口宽度的十分之一（方便计算），将 px 单位转换为 rem 单位即可适配（可使用插件）。

- 它本质上是“统一比例尺”的方案，适合整站一体化缩放。
- 但落地时经常要处理图表、边距、绝对定位的补偿逻辑。

- 当**视口宽高比 < 设计稿宽高比**，以宽高比 \* 视口宽度 / 10 进行 rem 适配。
- 当**视口宽高比 > 设计稿宽高比**，以 1 \* 视口宽度 / 10 进行 rem 适配。

```js
const html = document.documentElement
const screenRatioByDesign = 1920 / 1080
const screenRatio = html.clientWidth / html.clientHeight
const fontSize = ((screenRatioByDesign < screenRatio ? screenRatioByDesign / screenRatio : 1) * html.clientWidth) / 10
html.style.fontSize = fontSize.toFixed(3) + 'px'
```

### 3. vw/vh

按照设计稿的尺寸，将 px 按比例计算转为 vw 和 vh。

- 这是当前更推荐的大屏基线方案，因为它更符合响应式思维。
- 代价是图表、字体、边距通常还要针对具体场景做二次适配。

```scss
@use 'sass:math';

// 设计稿的宽度
$design-width: 1920;

// 设计稿的高度
$design-height: 1080;

// px to vw
@function vw($px) {
  @return math.div($px, $design-width) * 100vw;
}

// px to vh
@function vh($px) {
  @return math.div($px, $design-height) * 100vh;
}
```
