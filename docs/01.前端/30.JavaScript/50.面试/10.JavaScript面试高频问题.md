## 全局 `var` 与 `window`

### 短答

- 在浏览器里，顶层 `var` 声明的变量会成为 `window` 的同名属性。
- 但 `let`、`const` 不会挂到 `window` 上，它们只存在于全局词法环境里。

```js
var a = 1
let b = 2

console.log(window.a) // 1
console.log(window.b) // undefined
```

### 追问点

- `var` 会变量提升，初始值是 `undefined`。
- `let`、`const` 也会提升，但存在暂时性死区，声明前不可访问。
- 不是所有“全局变量”都等于 `window` 属性，这一点正是 `var` 和 `let/const` 的差异之一。

### 直接访问不存在的属性有什么区别

```js
console.log(window.notExist) // undefined
console.log(notExist) // ReferenceError
```

- 访问 `window` 上不存在的属性，结果通常是 `undefined`。
- 直接访问一个根本没有声明过的标识符，会触发 `ReferenceError`。
- 面试里可以用这点说明：“全局标识符访问”和“对象属性访问”不是一回事。

### `delete` 有什么区别

```js
var a = 1
window.b = 2

console.log(delete window.a) // false
console.log(delete window.b) // true
```

- 顶层 `var` 形成的全局属性通常是不可配置的，所以 `delete` 不掉。
- 直接给 `window` 挂的普通属性，如果是可配置的，通常可以被 `delete`。
- 这也是“全局 `var` 会挂到 `window`”但又不完全等同于“普通 window 属性”的关键差异。

### 可访问性差异

- 顶层 `var` 既可以直接通过标识符访问，也可以通过 `window.xxx` 访问。
- `let` / `const` 在全局作用域里可以直接访问，但不会成为 `window` 属性。
- 普通 `window` 属性可以通过 `window.xxx` 访问，但不一定总能作为未声明标识符被安全使用来理解业务语义。

### 四种情况对比表

| 场景               | 是否挂到 `window` | 是否可直接访问         | 不存在时的结果                | 是否通常可 `delete` |
| ------------------ | ----------------- | ---------------------- | ----------------------------- | ------------------- |
| 顶层 `var`         | 是                | 是                     | 已声明前为 `undefined`        | 否                  |
| 顶层 `let/const`   | 否                | 是                     | 声明前触发暂时性死区          | 否                  |
| `window.xxx = ...` | 是                | 通过 `window.xxx` 访问 | 不存在时是 `undefined`        | 通常是              |
| 未声明标识符       | 否                | 否                     | 直接访问触发 `ReferenceError` | 不适用              |

- 如果需要继续追问，可以顺着这张表过渡到属性描述符：顶层 `var` 对应的全局属性通常是不可配置的，而普通挂到 `window` 上的属性往往是可配置的。

## `this` 与绑定规则

### `this` 到底看什么

- `this` 不是函数定义时决定的，而是大多数情况下在调用时由 call-site 决定。
- 面试里最稳的答法是：先看调用方式，再判断 `this` 指向。

### call-site 是什么

- call-site 可以理解为“函数是在哪里、以什么形式被调用的”。
- 同一个函数，直接调用、对象调用、`call/apply/bind` 调用、`new` 调用，`this` 都可能不同。

```js
function show() {
  console.log(this)
}

const obj = { show }

show() // 普通调用
obj.show() // 对象调用
```

### 四种常见绑定规则

| 规则       | 典型写法       | `this` 指向                       |
| ---------- | -------------- | --------------------------------- |
| 默认绑定   | `fn()`         | 浏览器非严格模式下通常是 `window` |
| 隐式绑定   | `obj.fn()`     | 调用它的对象                      |
| 显式绑定   | `fn.call(obj)` | 显式传入的对象                    |
| `new` 绑定 | `new Fn()`     | 新创建的实例对象                  |

### 箭头函数的 `this` 有什么特殊

- 箭头函数不创建自己的 `this`。
- 它会捕获定义位置外层作用域的 `this`，而不是看谁调用它。

```js
const obj = {
  name: 'demo',
  run() {
    const inner = () => console.log(this.name)
    inner()
  },
}
```

- 这里箭头函数里的 `this` 来自 `run` 执行时的外层上下文。

### `new` 绑定做了什么

- 创建一个新对象
- 把新对象连接到构造函数的原型
- 用新对象作为 `this` 执行构造函数
- 如果构造函数没显式返回对象，就返回这个新对象

### 常见追问

- `bind` 不会立刻执行，它返回一个绑定过 `this` 的新函数。
- 箭头函数不适合拿来当构造函数，也没有自己的 `arguments`。
- “谁调用就指向谁”只适用于普通函数的部分场景，不能直接套在箭头函数上。

## 属性描述符与对象限制

### 冻结对象是如何实现“无法操作对象”的

- 本质上是通过属性描述符把对象属性改成不可写、不可配置，并禁止再扩展新属性。
- `Object.freeze(obj)` 可以近似理解为：
  - `Object.preventExtensions(obj)`
  - 把现有属性的 `writable` 设为 `false`
  - 把现有属性的 `configurable` 设为 `false`

### 什么是属性描述符

- 属性描述符是 JavaScript 用来定义“一个属性如何被读取、写入、枚举、配置”的元信息对象。
- 常见字段有：`value`、`writable`、`enumerable`、`configurable`、`get`、`set`。

```js
const user = {}

Object.defineProperty(user, 'id', {
  value: 1,
  writable: false,
  enumerable: true,
  configurable: false,
})
```

### 常见应用场景

- 定义只读属性
- 隐藏不想被枚举的内部字段
- 用 `getter/setter` 做访问拦截
- 做轻量响应式或数据校验

### `freeze` / `seal` / `preventExtensions` 区别

| 方法                       | 能否新增属性 | 能否删除属性 | 能否改写已有值 |
| -------------------------- | ------------ | ------------ | -------------- |
| `Object.preventExtensions` | 否           | 是           | 是             |
| `Object.seal`              | 否           | 否           | 是             |
| `Object.freeze`            | 否           | 否           | 否（浅层）     |

- 注意：`Object.freeze()` 默认是浅冻结，嵌套对象仍然可以改。

## 拷贝实现思路

### 浅拷贝

- 常见实现：`Object.assign`、展开运算符、`Array.prototype.slice()`。
- 问题在于：嵌套对象仍然共享引用。

### 深拷贝

| 方案                           | 优点             | 问题                                     |
| ------------------------------ | ---------------- | ---------------------------------------- |
| `JSON.parse(JSON.stringify())` | 简单             | 丢失 `undefined`、函数、`Date`、循环引用 |
| `structuredClone()`            | 原生、能力较完整 | 需考虑兼容性与不可克隆对象               |
| 手写递归                       | 可控             | 要处理循环引用、类型分支                 |

### 哪些对象不可克隆

- 常见不可克隆对象包括：函数、DOM 节点、`WeakMap`、`WeakSet`、`Symbol` 值。
- 如果对象内部包含这些不可克隆值，`structuredClone()` 也会直接失败。
- 面试里更稳的回答是：先说“不是所有 JS 值都能走 structured clone 算法”，再举 3 到 5 个典型例子。

```js
function deepClone(obj, cache = new WeakMap()) {
  if (obj === null || typeof obj !== 'object') return obj
  if (cache.has(obj)) return cache.get(obj)

  const result = Array.isArray(obj) ? [] : {}
  cache.set(obj, result)

  for (const key of Reflect.ownKeys(obj)) {
    result[key] = deepClone(obj[key], cache)
  }

  return result
}
```

### 追问点

- 面试官常追问：循环引用怎么处理、函数怎么处理、原型链要不要保留。

## 性能优化高频题

### 白屏时间看什么

- 先看资源加载链路：HTML、CSS、JS 是否阻塞首屏。
- 再看是否有大体积同步脚本阻塞解析。
- 还要看接口依赖是不是把首屏渲染卡死了。

### 长任务怎么优化

- 主线程上超过 50ms 的连续任务通常就会让交互卡顿。
- 常见手段：拆分任务、延迟非关键逻辑、减少同步计算、把计算移到 Worker。

### 动画为什么会卡

- 常见原因不是“动画 API 不行”，而是主线程忙、布局抖动、频繁读写 DOM。
- 优先策略：
  - 使用 `requestAnimationFrame`
  - 尽量只动 `transform` / `opacity`
  - 合并 DOM 读写，避免强制同步布局

```js
function move(el, x) {
  requestAnimationFrame(() => {
    el.style.transform = `translateX(${x}px)`
  })
}
```

### 回答性能题的主线

1. 先定位瓶颈在资源、脚本、渲染还是网络。
2. 再区分首屏问题还是交互问题。
3. 最后给出最小可落地优化策略。

## 浏览器 API 高频题

### 最常问哪些 API

| 类型   | 高频 API                                                   | 常问点                               |
| ------ | ---------------------------------------------------------- | ------------------------------------ |
| 存储   | `localStorage` `sessionStorage` `cookie` `IndexedDB`       | 区别、容量、生命周期、是否随请求发送 |
| 通信   | `postMessage` `BroadcastChannel` `WebSocket`               | 跨源、广播、服务端中转               |
| 调度   | `requestAnimationFrame` `requestIdleCallback`              | 适用场景、时机差异                   |
| 观察器 | `IntersectionObserver` `MutationObserver` `ResizeObserver` | 替代轮询、性能收益                   |
| 网络   | `fetch` `AbortController`                                  | 请求取消、错误处理、流式能力         |
| 缓存   | `Cache Storage` `Service Worker`                           | 离线缓存、资源命中、更新策略         |

### 存储类 API 怎么答

- `localStorage`：持久化存储，同源共享，容量有限，API 简单。
- `sessionStorage`：会话级存储，标签页关闭后失效。
- `cookie`：体积更小，会随请求自动发送，适合会话标识但不适合存大量业务数据。
- `IndexedDB`：适合大体量结构化数据，能力强但使用复杂。

| API              | 兼容性/生态        | 常见替代方案                   | 常见坑                               |
| ---------------- | ------------------ | ------------------------------ | ------------------------------------ |
| `localStorage`   | 兼容性好           | `IndexedDB`                    | 同步 API，频繁写入会阻塞主线程       |
| `sessionStorage` | 兼容性好           | 页面内状态管理                 | 标签页隔离，不会跨标签共享           |
| `cookie`         | 兼容性极好         | `localStorage`、服务端 Session | 会随请求自动发送，滥用会增大请求体积 |
| `IndexedDB`      | 现代浏览器支持较好 | `localStorage`                 | API 心智负担高，事务和版本升级要处理 |

### 通信类 API 怎么答

- `postMessage`：适合已持有窗口引用时的跨源定向通信。
- `BroadcastChannel`：适合同源多标签页广播。
- `WebSocket`：适合服务端中转的实时通信，不是简单替代前两者。

| API                | 兼容性/生态      | 常见替代方案     | 常见坑                         |
| ------------------ | ---------------- | ---------------- | ------------------------------ |
| `postMessage`      | 兼容性好         | `MessageChannel` | 忘记校验 `origin`              |
| `BroadcastChannel` | 现代浏览器更友好 | `storage` 事件   | 只支持同源，使用后要关闭通道   |
| `WebSocket`        | 工程中常用       | SSE、轮询        | 要自己处理重连、心跳、断线恢复 |

### 调度类 API 怎么答

- `requestAnimationFrame`：适合动画和视觉更新，时机贴近浏览器下一帧渲染。
- `requestIdleCallback`：适合非紧急任务，但要考虑兼容性，不能拿来做核心逻辑。

| API                     | 兼容性/生态    | 常见替代方案 | 常见坑                                 |
| ----------------------- | -------------- | ------------ | -------------------------------------- |
| `requestAnimationFrame` | 浏览器支持较好 | `setTimeout` | 不适合做高耗时计算                     |
| `requestIdleCallback`   | 兼容性一般     | 延迟任务切片 | 空闲时间不稳定，不能依赖它完成关键逻辑 |

### 观察器类 API 怎么答

- `IntersectionObserver`：常用于懒加载、曝光统计、无限滚动。
- `MutationObserver`：观察 DOM 结构变化。
- `ResizeObserver`：观察元素尺寸变化。
- 共同优势是：比手动轮询更省性能。

| API                    | 兼容性/生态        | 常见替代方案      | 常见坑                                 |
| ---------------------- | ------------------ | ----------------- | -------------------------------------- |
| `IntersectionObserver` | 现代浏览器支持较好 | 滚动事件 + 节流   | 阈值和根容器设置不当会误判             |
| `MutationObserver`     | 支持较广           | 轮询 DOM          | 观察范围过大可能带来额外开销           |
| `ResizeObserver`       | 现代浏览器支持较好 | `window.onresize` | 只能观察尺寸变化，不等于布局稳定后事件 |

### 网络类 API 怎么答

```js
const controller = new AbortController()

fetch('/api/user', { signal: controller.signal })
controller.abort()
```

- 高频追问：`fetch` 为什么对 HTTP 4xx/5xx 默认不 reject、怎么取消请求、和 XHR 有什么差异。

| API               | 兼容性/生态        | 常见替代方案   | 常见坑                           |
| ----------------- | ------------------ | -------------- | -------------------------------- |
| `fetch`           | 现代浏览器主流方案 | XHR、Axios     | HTTP 失败状态默认不 reject       |
| `AbortController` | 现代浏览器支持较好 | 自定义取消标记 | 只取消信号，不会自动处理业务兜底 |

### 浏览器 API 面试主线

1. 先说这个 API 解决什么问题。
2. 再说它和相近 API 的边界差异。
3. 最后补兼容性、性能收益和常见坑。

## DOM / BOM 高频题

### 事件委托是什么

- 事件委托是把子元素的事件处理逻辑挂到共同父元素上，利用事件冒泡统一处理。
- 核心价值是：减少重复绑定，适合动态列表和批量节点。

```js
document.querySelector('#list').addEventListener('click', (event) => {
  const item = event.target.closest('li')
  if (!item) return

  console.log(item.dataset.id)
})
```

- 高频追问：为什么能工作、依赖事件冒泡、哪些事件不适合直接委托。

### 原生 DOM 高频点

| 主题     | 常问点                                         | 回答抓手                    |
| -------- | ---------------------------------------------- | --------------------------- |
| 获取节点 | `querySelector` 和 `getElementById` 区别       | 选择能力与返回范围          |
| 监听事件 | `addEventListener` 与 `onclick` 区别           | 可绑定多个监听器、捕获/冒泡 |
| 修改节点 | `innerHTML`、`textContent`、`appendChild` 区别 | 安全性、性能、是否解析 HTML |
| 节点关系 | `parentNode`、`children`、`nextElementSibling` | DOM 树遍历                  |

### BOM 高频点

| `screen`    | 屏幕宽高信息                 | 大屏和设备判断 |

### 常见追问

- 事件委托为什么适合动态节点：因为后加的子节点也会冒泡到父级。
- `innerHTML` 为什么有风险：会解析字符串为 HTML，存在 XSS 面风险。
- `history.pushState` 和 hash 路由差异：一个改历史记录不刷新页面，一个基于 URL hash。

### DOM / BOM 回答主线

1. 先说对象或 API 解决什么问题。
2. 再说事件流、节点关系或浏览器对象边界。
3. 最后补性能、安全性和适用场景。

## 模块化与构建高频题

### ESM 和 CommonJS 有什么区别

| 维度     | ESM                               | CommonJS                 |
| -------- | --------------------------------- | ------------------------ |
| 语法     | `import/export`                   | `require/module.exports` |
| 加载时机 | 静态分析友好                      | 运行时加载               |
| 值语义   | live binding                      | 值拷贝/引用结果          |
| 运行环境 | 浏览器、现代构建工具、Node 新规范 | Node 传统生态            |

- 面试短答：ESM 更适合静态分析和构建优化，CommonJS 更灵活但不利于 tree-shaking。

### 为什么 ESM 更利于 tree-shaking

- 因为 `import/export` 是静态语法，构建阶段就能知道依赖关系。
- 构建工具更容易判断“哪些导出没被使用”，从而在打包时删掉死代码。

### tree-shaking 是什么

- tree-shaking 本质上是“基于依赖图删除未使用代码”的优化过程。
- 它依赖静态分析，不是所有写法都能被安全消除。

### 哪些情况会影响 tree-shaking

| 场景                   | 为什么会受影响               |
| ---------------------- | ---------------------------- |
| CommonJS 导出          | 运行时特性更强，静态分析更难 |
| 模块有副作用           | 构建工具不敢随便删除         |
| 动态导入/动态访问导出  | 使用边界不够静态             |
| 聚合导出过多且引用不清 | 依赖追踪复杂度提高           |

### 常见追问

- `default export` 不是不能 tree-shake，但具名导出通常更利于分析和维护。
- `sideEffects` 字段不是“优化开关”本身，而是告诉构建工具哪些文件有副作用、不能乱删。
- tree-shaking 不是运行时能力，而是构建阶段能力。

### 面试回答主线

1. 先讲模块系统差异：ESM 静态、CommonJS 动态。
2. 再讲为什么静态语法更适合构建优化。
3. 最后补副作用、打包边界和工程配置。
