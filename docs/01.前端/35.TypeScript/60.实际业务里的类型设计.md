# TypeScript 实际业务里的类型设计

## 阅读建议

- 这页重点不是只讲语法技巧，而是解释业务代码里为什么要设计类型、怎么设计更稳、怎么避免类型越来越乱。

## 核心目标

- 看完后能知道在真实业务里，类型设计的重点不是“炫技”，而是边界清晰、约束合理、可维护。

## 业务里的类型设计先看什么

| 方向 | 先想什么                           |
| ---- | ---------------------------------- |
| 输入 | 这个函数、组件、接口接收什么       |
| 输出 | 最终返回什么结构                   |
| 状态 | 哪些字段一定有，哪些字段可能没有   |
| 阶段 | 同一个对象在不同阶段有没有不同形态 |

## 最常见的类型设计场景

| 场景        | 设计重点                         |
| ----------- | -------------------------------- |
| API 响应    | 区分服务端原始结构和前端使用结构 |
| 表单数据    | 区分初始化值、编辑值、提交值     |
| 组件 props  | 区分必填、可选、默认值、回调     |
| 列表项      | 保证最小必要字段清楚稳定         |
| 状态机/流程 | 用联合类型区分不同状态           |

## 最小示例

```ts
type UserApi = {
  id: number
  nickname: string
  avatar?: string
}

type UserCard = {
  id: number
  name: string
  avatarUrl?: string
}
```

- 这里的重点不是类型多，而是“接口原始结构”和“页面消费结构”不强绑在一起。

## 设计时更稳的做法

1. 先把输入输出边界写清。
2. 先保证核心字段稳定，再谈工具类型复用。
3. 不要把所有业务状态都压成一个超大类型。
4. 阶段不同就拆类型，不要靠注释硬解释。

## 常见设计方式

| 方式         | 适合什么问题     |
| ------------ | ---------------- |
| 基础对象类型 | 描述稳定结构     |
| 联合类型     | 表达不同状态     |
| 工具类型     | 做局部裁剪和变形 |
| 泛型         | 抽象共性模式     |

## 常见误区

- 直接把后端返回类型到处复用，导致前端边界混乱。
- 一个类型承载太多阶段状态，后面越来越难收紧。
- 为了“灵活”大量使用 `any`，最后失去约束价值。
- 一上来写很复杂的泛型，反而掩盖真实业务结构。
